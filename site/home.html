落として、砕く

硬い物体なので体積は全フレームで 8.00000。ばらつきは 0.0000000 だった。

煙の減り方を式にする

毎フレーム (1−d) 倍という仮説を立て、実測と4桁一致させた。

毛を生やす

density は本数ではなく面積あたりの本数。100 を入れて 1,249本、面積 12.53 で割ると 99.678。

曲げても痩せない骨

90度曲げたときの体積の減りが Linear で 27.1284%、Dual Quaternion で 0.1764%。

塊を滑らせて、摩擦を式で確かめる

MPM の Ground Friction は教科書のクーロン摩擦の μ そのもの。止まる距離が式と 0.04% で合った。ただし塊が潰れ始めると式から外れる。

ノイズはどこまで減るのか

サンプル数を4倍にすればノイズは半分、という式は狭い範囲でしか当たらなかった。指定した数がそのまま使われていない。

届かない場所を指す

逆運動学で届かない目標を指すと、腕は伸びきってそこで止まる。9通りすべてで式と全桁一致。

風を当てる

風速だけ上げても何も起きない。風は空気抵抗を通してしか効かず、その抵抗は速さの2乗だった。

    木の代わりに細い円錐を1本作る。太さを上下で変えて先細りにした。そして回転を X に 90 度かけて、Z 軸方向に倒しておく。理由は次の段で分かる。

    Houdini のパラメータ画面

  6. 点の上に複製するcopy to points

    1本目の入力に円錐、2本目に点をつなぐ。点が持っている N に合わせて、1本ずつ向きが決まる。最後に地面と合流させれば完成。

つまずくところ

テンプレートは Z 軸に伸ばす

は、の Z 軸を N に合わせる。Y 軸に立ったままの円錐を渡すと、200個すべてが90度倒れる。実験008で200個すべての角度を測ったところ、Y軸のままだと 90.00°、Z軸に倒しておくと 0.00° だった。

tube の既定は面ではない

tube の type は既定が Primitive で、点が1個・面が1枚しか出てこない。複製しても何も見えないので、Polygon に変える。

normal は、ばらまく前に

を通すと面が無くなり点だけになる。そのあとで normal をかけても N は作れない。順番を逆にすると、木が向きを失って全部同じ方向を向く。

つまずくところ

点を増やさずに細かくしても無駄

elementsize を小さくしても、点が足りなければ表せない。実験004では、重ねるノイズの枚数（oct）を 3 から 8 に増やしても、点が足りない間はまったく変化がなかった。点を増やして初めて効き始める。

パラメータ名が思っているものと違う

roughness や octaves という名前は存在しない。実際の名前は rough / oct / lac。一般的な名前で書くとエラーになる。

ノイズを先にかけると、あとの分割でならされる

実験003で測ったところ、分割してからノイズをかけると凹凸のずれが最大 0.08062、逆の順だと 0.03671 だった。約2.2倍の差がある。分割は周りの点を平均するので、先に作った凹凸をなめしてしまう。

つまずくところ

引く形は貫通させる

円柱が箱より短いと、途中で止まった袋小路の穴になる。上下にはみ出す長さにしておくのが確実。

結果が正しいかは体積で検算できる

実験012で確かめたところ、和と積の合計が元の2つの合計と一致し（差 0.0000049）、差の体積も関係式とちょうど 0 の差で一致した。見た目で判断がつかないときは、この関係式で確かめられる。

boolean には8つの演算がある

よく使う Union（和）/ Intersect（積）/ Subtract（差）のほかに、Shatter（A を砕いて全部の破片を残す）、Seam（境界線だけを出す）、Detect（検出だけして形は変えない）、Resolve（自分自身の重なりを解消する）がある。Shatter の体積は元の箱と完全に一致した（どちらも 8.00000）ので、破壊の下ごしらえに使える。Seam は面数 6 のまま体積 0 になる。

ポリゴンの球は rows / cols では割れない

sphere で rows / cols を 30 にしても、面数は 80 のまま変わらなかった。球は多面体を細分する別のやり方で作られている。しかもその粗い球の体積は 9.00180 で、同じ半径の真球 10.30575 より 13% 小さい。ポリゴンで近似した球は必ず内側に寄るので、体積を当てにするなら分割を上げる。

つまずくところ

実行対象で、できるものの置き場所が変わる

class を「点ごと」にすれば点の属性、「面ごと」にすれば面の属性になる。同じコードでも置き場所が変わるので、あとのノードが見つけられなくなることがある。

他のノードの値を読むときは op: を付ける

パスをそのまま書くと、エラーも警告も出ないまま 0 が返る。頭に op: を付けるのが正しい。気づきにくいので覚えておく。

速いが、ループの代わりになるとは限らない

実験010で、 ループを VEX に書き換えたら 3,969面で 85.9倍速くなった。ただし for-each には「かたまりを切り離す」働きもあり、そこが必要な場合は置き換えられない。速さだけで選ぶと目的を失う。

速さを測るのは難しい。三度失敗した

一度目：cook(force=True) の前後を時計で挟んだ。計算量を100倍にしても時間は 0.9倍にしかならない。ジオメトリを要求した時点で初めて計算されるので、計測区間の外で処理が走っていた。二度目：Houdini の性能計測機能を使ったが、軽い処理も重い処理も同じ 0.008000 秒を返す。が効いていた。三度目：毎回新しいノードを作って初回のを測る。これでようやく、計算量100倍の処理が 17.7倍の時間になった。

VEX が速いのは、点が多いときだけ

64万点に sin×cos を1回かける処理が 2.47ミリ秒、256万点で 4.58ミリ秒。この2点から、1点あたりの限界コストは約1.1ナノ秒（毎秒約9億点）、固定の費用が約1.8ミリ秒と分かる。4万点では 1.49ミリ秒かかっており、そのほとんどが固定費。少ない点数なら、どう書いても体感は変わらない。

rand(@ptnum) は毎回同じ値を返す

同じコードを別のノードで2回走らせて、全400点が小数点以下9桁まで一致した。乱数といっても点番号から決まる固定の値なので、実行するたびに変わることはない。だから結果が再現するし、逆に「毎回違う値」が欲しいなら種を自分で変える必要がある。

つまずくところ

gridsamples では解像度が変わらない

名前は「Grid Samples」だが、これを 128 にしても 1024 にしても 100×100 のまま動かない。解像度を決めるのは size ÷ gridspacing。細かくしたいときは gridspacing を下げる。実験034で確かめた。

flowdir.x と flowdir.y は入れ替えて使う

浸食が残す「水の流れた向き」は flowdir.x と flowdir.y の2枚に分かれている。地形は水平なので、素直に set(fx, 0, fy) と書きたくなるが、これだと下り坂を向かない（実験036で測った平均は 96.5度＝でたらめ）。8通り総当たりで試したところ、入れ替えた set(fy, 0, fx) だけが平均 39.9度まで下がった。

normal SOP が書くのはバーテックスの N

点のラングルから @N を読んでも空のまま。実験036では、これに気づかず草の向きがでたらめになった。点の N が要るなら、attribpromote でバーテックスから点へ移すか、この手順のように高さから自分で計算する。

v@flow という名前は使えない

convertheightfield はレイヤーを点アトリビュートとして持ってくるので、float の flow がすでに点に乗っている。そこへ v@flow とベクトルで書こうとすると型がぶつかる。実験036でこれに掛かった。名前を変える。

浸食の時間は回数に比例しない

つまずくところ

rigdoctor の3つのトグルは、すべて既定オフ

そのまま通しても何も足されない。transformations / inittransforms / outputparentidx を入れて初めて属性が出てくる。エラーは出ないので、属性が付いているかを自分で確かめる。

rotate と prerotate を取り違えると、関節ごと飛んでいく

rotate() だと「動かしてから回す」になり、回した関節そのものが原点のまわりを回ってしまう。90度で先端が (−2, 0, 0) に飛び、正しい値 (−1, 1, 0) とのずれは 1.41。30度だと「少し曲がった骨」に見えてしまい、絵では気づけない。大きく振ると差が開くので、確かめるときは90度まで回す。

曲げると痩せる。減り方には式がある

既定の Linear では、体積の減りが 27.1284% × (1 − cos θ) にぴたり乗る。6通りの角度すべてで、(1 − cos θ) で割った値が 27.1284〜27.1286 にそろった。90度で 27.13%、120度で 40.69%。ねじり（骨の軸まわり）だともっとひどく、179度で 66.81% 減る。

痩せる原因は maxinfluences の既定 2

1つの点が2本の骨に従うので、関節の近くで2つの行列が混ざる。混ざった結果は、どちらの行列でもない縮んだ位置になる。1 にすると減りは 0.85% まで落ち、根元の点はぴくりとも動かなくなるが、関節が鋭く折れる。3 にするともっと減る（36.84%）。「なめらかにしたいから骨を増やす」は逆効果。

「2つの中間」は、属性が無いと動かない

jointdeform の method を「Blend Dual Quaternion and Linear」にすると「Missing dual quaternion blend attribute」で止まる。点ごとの混ぜ具合を表す float のアトリビュートを自分で作り、名前を dqblendattrib に入れる。全点に 0.5 を入れると、減りは 14.69% で Linear のほぼ半分になった。

Dual Quaternion にも癖がある

ねじれが根元まで広がる。170度ひねったとき、根元の帯は Linear で 14.1度しかねじれないのに、Dual Quaternion では 58.9度ねじれる。さらに、99.2度で止まっている帯のすぐ上が 170度になり、途中に段差ができる。体積は保たれるが、形が素直とは限らない。

materialpreset は、スクリプトから変えても何も起きない

Material Preset のメニューを10通り全部試して、結果は9桁まで完全に同じだった。エラーも警告も出ない。実際に効くのは materialtypeのほうで、こちらを変えると結果がはっきり変わる（実験062）。理由も確かめた。この項目には recipeutils.setPresetMenu というコールバックが付いていて、UI で触ったときにしか走らない。スクリプトから parm().set() しても、値が入るだけでコールバックは走らない。

mpmsolver の Ground Plane は groundactive が既定で 1。コライダを一つも置いていないのに、粒が y ≈ 0.3 で止まって混乱した。自由落下を測りたいときは、これを切る（実験066）。

描画（レンダリング） シミュレーション キャッシュ VEX とリグ 時間の測り方

描画（レンダリング）

  1. 確認用の描画は OpenGL、見せる絵だけ Karma にする

    煙で OpenGL 0.71秒 対 Karma 3.64秒（256サンプル）で約5倍。地形では 1.29秒 対 3.20秒で2.5倍。毛では本数が増えるほど差が開き 4.1倍 → 17.4倍。OpenGL は毛の本数によらず 0.74〜0.76秒で一定だった。

  2. サンプル数は 32 前後で頭打ち。上げる前にしきい値を疑う

    samplesperpixel は上限であって指定ではない。64 → 4096 に64倍しても、実効サンプル数は 99 → 567 の5.7倍にしかならなかった。本当に詰めるなら varianceaa_thresh（既定 0.01）も下げる。0.0002 まで下げると時間は 5.39秒 → 70.64秒で13倍になる。

  3. 軽い絵を何枚も撮るなら、サンプル数より枚数が効く

    640×360 で固定費が 2.26秒、1サンプルあたり 7.44ミリ秒。2サンプルでは時間のほぼ全部が固定費で、256サンプルでも半分強が固定費だった。

  4. 凸凹を bump で付けると一番遅い

    bump は 8.32秒で、何もしない場合の1.9倍。点を動かさない displacement（6.32秒）より遅かった。「面を動かさないから軽い」とは限らない。遅い理由は未確認。

  5. テクスチャの解像度は、見える大きさに見合えば十分

    256 → 1024 に4倍しても、画の細かさは 2.9028 → 3.0095 の1.04倍にしかならなかった。この見え方の大きさなら 256 でほぼ足りる。

  6. 毛は太くすると時間が倍になる。本数は増やしても比例しない

    太さ 0.001 → 0.008 で 5.0秒 → 10.7秒。本数を16倍にしても時間は4.2倍で、1本あたりは 0.9841ms → 0.2630ms と3.7分の1になる。

  7. 色を付けても重くならない

    毛に色を付けたときのレンダ時間は 8.0秒 / 8.0秒 / 8.1秒。色は形の複雑さを増やさない。

  8. 発光（Emission）はライトを1つ足すのと同じくらい重い。まわりを照らさないなら emitillum を切る

    同じ絵で Emission 0 が 3.79秒、64 が 12.35秒（3.3倍）。Emission 16 のまま Emission Illuminates Objects を切ると 10.27秒 → 3.40秒（3.0倍速い）。切っても文字は光ったままで、床の明るさだけが発光0のときと同じ 96.89 に戻る。

  2. substep を上げるなら 8 が落としどころ

    MPM で 16 との差が 高さ 0.004984 / 広がり 0.002012 / 体積比 0.003627 まで縮み、時間は 16 の53%。半分の時間でほぼ同じ結果。

  3. 粒は増やすほど1粒あたりが安くなる

    MPM で 238粒のとき1粒 284.32µs、4,602粒で 20.11µs。14分の1。1フレーム進める時間はどれも 0.06〜0.09秒で、ほとんどが固定費だった。

  4. 面に戻すときの細かさは voxelscale ではなく粒の間隔で決める

    mpmsurface の voxelscale を細かくすると点の数は 5,495 → 23,485 の4.3倍になるのに、形（体積）はほとんど変わらない。重くなるだけ。

  5. HeightField の侵食は回数に比例しないが、4回あたりから重くなる

    100×100 で 1回 0.68秒、2回 0.80秒、4回 2.35秒。1回目に下ごしらえの費用がかかり、そのあとは増えていく。実用の解像度では相応に重い。

  6. 曲がらない物のコライダは Animated (Rigid) にする

    同じ MPM の場面で Static 3.05秒・Rigid 3.83秒・Deforming 8.98秒。Deforming は Rigid の2.3倍かかる。形が変わらない板なら、2つの答えはほぼ同じ（5.336132 対 5.335937）。ただし曲がる板を Rigid にすると、たわみが平均の上下動に置き換わる。

  7. Liquid の粒が飛ぶ暴れは、substep 8 で止める。2 や 4 では足りない

    Liquid を摩擦のある地面に置くと、F28〜46 から数粒が飛び始めた。substep 8 で消えたが、時間は 60フレームで 2.82秒 → 13.16秒（4.7倍）、120フレームで 5.36秒 → 33.85秒（6.3倍）。摩擦を 0 か 1.5 以上にしても暴れなかった。

  8. MPM の摩擦を効かせたいなら、substep ではなく粒の間隔を細かくする

    回る台の滑り出しで、substep 1 / 4 / 8 は境目がまったく同じなのに時間は 3.48秒 → 17.58秒（5.1倍）。粒の間隔 0.12 → 0.04 なら実効の摩擦が 0.34 → 0.79 に上がり、時間は 4.04秒 → 5.37秒（1.3倍）で済んだ。

  9. RBD の破片を増やしても、割る時間はほぼ変わらない。効くのは解く時間

    壁を 10 / 25 / 50 / 100 / 200個に割ると、割る時間は 1.10〜1.28秒でほぼ一定。60フレーム解く時間は 0.26 / 0.29 / 0.40 / 0.56 / 1.15秒（破片20倍で4.4倍）。ただし細かいほど崩れやすくなるので、強さも決め直す。

キャッシュ

  1. 何度も見るシミュレーションはキャッシュする。得になるのは2回目から

    煙の読み込みが 1.17秒 → 0.26秒で4.6倍速くなった。重いシミュレーションほど差は開く。初回の書き出しには計算の時間がそのまま乗る。 手順「シミュレーションをキャッシュする」の煙 40フレームでは、フレームを送るだけの時間が 0.99〜1.01秒 → 0.06秒（約17倍）。実験025は値の集計込みで測った。

  2. キャッシュのフレーム範囲は数値で入れる。式のままだと無駄に書き出す

    フレーム範囲の指定でつまずき、意図の6倍のファイル（3,578.9MB・28.81秒）を書いた。式を消して数値を入れると 63.3MB・0.15秒。56倍の無駄だった。

VEX とリグ

  1. 面ごとの処理は for-each より VEX で書く

    for-each は面の数に比例して遅くなる（49面 11.79ミリ秒、3,969面 191.87ミリ秒）。VEX はほぼ一定（1.36 → 2.23ミリ秒）。差は 3,969面で85.9倍。 作ったあとで上流を動かして計算し直させると差はさらに開き、3,969面で 167ミリ秒 対 0.8ミリ秒（約200倍。手順「面ごとの繰り返しを VEX に置き換える」）。

  2. 点が少ないうちは、どう書いても速さは変わらない

    VEX のノード1つに約1.8ミリ秒の固定費があり、1点あたりは約1.1ナノ秒。4万点では 1.49ミリ秒のほとんどが固定費だった。

  3. スキンの混ぜ方は、速さを理由に選ばなくてよい

    414,720点で Linear 14.66ミリ秒、Dual Quaternion 15.21ミリ秒。1.04倍。5通りの大きさで 0.98〜1.12 に収まる。

  4. 細かい形をたくさん配るなら、Pack and Instance を入れる

    2,210点の球を1万個配ると、Pack なしは 2,210万点・1,878MB・714ms。Pack ありは 1万点・4.1MB・2.9ms（約250倍速く、メモリは約460分の1）。

時間の測り方

  1. 毎回新しいノードを作って、初回の計算を測る

    計算の前後を挟むだけだと、計算量を100倍にしても時間が0.9倍にしかならなかった。ジオメトリを要求した時点で計算が走るので、区間の外で処理していた。新しいノードの初回を測ると、100倍の処理が17.7倍の時間になり、結果も動いた。

  2. 1回目の時間は捨てる

    1回目には下ごしらえの費用が乗る。HeightField の侵食では1回目だけ費用が大きく、MPM でも最初の1回を捨ててから測っている。 Karma も、起動直後の1枚目は 19.49秒、続けて撮り直すと 3.49秒だった（同じ地形・同じ設定、手順「Karma で見せる絵を撮る」を作ったとき）。

  3. 比べたいものだけを測る

    Linear と Dual Quaternion の比較では、両方に共通する結び付け（capture）を先に済ませてから測った。そうしないと共通の重い処理が時間に混ざる。

  4. 粒の値は1粒ずつ読まず、まとめて受け取る

    15,591粒の位置を1粒ずつ position() で読むと1フレーム 81.67ms で、MPM の計算そのもの（約 86ms）と同じだけかかった。速さも読むと 226.34ms。pointFloatAttribValues なら 0.57ms、numpy.frombuffer(pointFloatAttribValuesAsString) なら 0.11ms（740倍速い）。読んだ値は6桁まで同じ。

  5. 点の数は len(g.points()) ではなく intrinsicValue("pointcount") で数える

    2,210万点を len(g.points()) で数えると、Python の一覧を作るだけで約8.8秒かかり、測りたかった計算（714ms）の12倍になった。

mpmsolver

SOP

時間を進めて粒を動かす。地面も重力も風もここ。

入力は 0 = 源 / 1 = ぶつかるもの / 2 = 範囲。コライダが要らないなら 1 は空でよい。重力・空気抵抗・風・地面・substep が全部この1ノードにある。

  • gravityy重力。既定 −9.81
  • airdrag空気抵抗。既定 0。速さの2乗に比例する
  • windvelocityx / y / z風速。airdrag が 0 だと何も起きない
  • groundactivey = 0 の地面。既定 1（入っている）
  • groundfriction地面の摩擦。クーロン摩擦の μ そのもの。既定 1.0
  • groundsticky地面の粘着。既定 0。横滑りではなく離れるときに効く
  • globalsubsteps1フレームを何回に分けるか。既定 1
  • exportv / exportje / exportjp速度や体積比を粒に書き出すか。既定オン

mpmcollider

SOP

粒がぶつかる物を作る。

入力は 0 = 形、1 = mpmcontainer。渡した形を VDB に変えて、mpmsolver の入力1につなぐ。動かしたいときはアニメーションした形をそのまま渡す。

  • typeStatic（既定）/ Animated Rigid / Animated Deforming。動かすなら Static のままにしない
  • friction摩擦。既定 1.0。組み込みの地面と同じ式
  • sticky粘着。既定 0.0
  • computevelocity既定オン。Rigid では無関係だが、Deforming では切ると動かなくなる
  • voxelsizeoverride / voxelsizeVDB の目の細かさ
つまずいた点mpmsolver が最初から y = 0 に地面を持っているので、同じ高さに床を置くと コライダの摩擦が完全に無視される。地面 0.0・コライダ 1.0 でも、摩擦なしの距離と6桁まで同じ値になった。効くのは「先に触った面」だけで、地面を下げるとコライダが勝つ。床を自分で置くなら groundactive を 0 にする（実験069）。もうひとつ、type の既定は Static。板を動かしても粒は何も感じない。Animated (Rigid) に変えて初めて動く。エラーも警告も出ない（実験070）。摩擦の式そのものは地面と同じで、5通りの摩擦で差は 0.6% 以内だった。

Terminology

用語集

Houdini は略語と英語の専門用語が多い。前提知識なしで読めるようにまとめた。 本文中の点線が付いた語は、押すとその場で意味が出る。

ネットワークと文脈 ジオメトリの構成要素 よく使う処理 シミュレーション 表示とレンダリング Houdini そのものに関する語

ネットワークと文脈

Houdiniは「どの階層で作業しているか」で使えるノードが変わる。その階層の名前が SOP や DOP といった略語になっている。

ノード / Nodeノード
ひとつの処理を表す箱。入力を受け取り、加工して出力する。Houdiniではこの箱をつないで結果を作るため、作業そのものが「箱をつなぐこと」になる。
ネットワーク / Networkネットワーク
ノードをつないだ全体のこと。上から下へ流れる図として表示され、これを編集する画面をネットワークエディタと呼ぶ。
SOPソップ · Surface Operator
ジオメトリ（形）を扱うノードの階層。box、mountain、subdivide など、モデリングで使うノードはほぼSOP。Houdiniで最初に慣れるべき場所。関連: ジオメトリ
POPポップ · Particle Operator
パーティクル（粒子）を扱うノードの系統。火花、雨、群衆のように「たくさんの小さなものが動く」表現に使う。シミュレーション用のネットワークの中で組む。関連: DOP, シミュレーション
DOPドップ · Dynamics Operator
シミュレーション（物理計算）を扱う階層。破壊、布、煙、液体などはここで計算する。時間をフレームごとに進めながら結果を積み上げていくのが特徴。関連: ソルバ, シミュレーション
VOPボップ · VEX Operator
VEXの処理をノードをつないで組み立てる階層。コードを書く代わりに図で書くVEX、という位置づけ。関連: VEX
ROPロップ · Render Operator
出力を担当するノードの階層。画像のレンダリング、ファイル書き出しなど「最終的に何かを外に出す」処理はここ。関連: Karma, OpenGL ROP
OBJオブジェ · Object
シーンに置く「物体」の階層。カメラ、ライト、ジオメトリの入れ物（geoノード）などが並ぶ。SOPはこのgeoノードの中に入っている。
LOPロップ · Lighting Operator
USDベースでシーンを組む階層。Solarisとも呼ばれる。ライティングやレンダリングの設定を扱う新しい仕組み。
プロシージャルモデリング / Procedural modelingプロシージャルモデリング
形を手で作り込むのではなく、手順（ノードのつながり）として組み立てるやり方。あとから数値を変えるだけで作り直せるのが利点で、Houdini の中心的な考え方。関連: ノード / ネットワーク
エフェクト / FXエフェクト
破壊・煙・炎・水・パーティクルなど、時間とともに変化する表現の総称。形を作るモデリングに対して、動きを計算させる側を指す。関連: シミュレーション
チャンネル / Channelチャンネル
ノードの入出力を役割ごとに分けた筋道。FLIP では「液体の粒」「容器」「衝突」の3つのチャンネルが並んで流れており、対応する入口と出口をつなぐ必要がある。関連: FLIP

ジオメトリの構成要素

Houdiniは形を「ポイント」「バーテックス」「プリミティブ」に分けて扱う。ここの区別が分かるかどうかで理解度が大きく変わる。

ジオメトリ / Geometryジオメトリ
形のデータそのもの。ポイントやプリミティブの集まりを指す。ノードからノードへ流れていくのはこのジオメトリ。
ポイント / Pointポイント
空間上の位置を持つ点。位置は必ず P という属性として持っている。形の頂点にあたるが、Houdiniでは「位置を持つだけの存在」として独立している。関連: バーテックス, P
バーテックス / Vertexバーテックス
プリミティブ（面）の角。どのポイントを使うかを指し示すだけの存在。2つの面が同じ角を共有している場合、ポイントは1つだがバーテックスは2つある。UVや面ごとの法線はこちらに乗る。初心者が最も混乱する区別。関連: ポイント, プリミティブ
プリミティブ / Primitiveプリミティブ
面や線、ボリュームなど「形の単位」。ポリゴン1枚がプリミティブ1つ。立方体なら6面あるのでプリミティブは6つ。prim と略される。関連: ポリゴン, バーテックス
ポリゴン / Polygonポリゴン
3つ以上のバーテックスで囲まれた面。プリミティブの一種で、モデリングで最もよく使う種類。
アトリビュート / Attributeアトリビュート
ジオメトリに付けられる名前付きのデータ。位置、色、速度、大きさなど何でも持たせられる。Houdiniの柔軟さの正体はこれで、「必要な情報を自分で作って後段のノードに渡す」のが基本的な考え方。属性とも書く。関連: P, N, Cd, ディテールアトリビュート
Pピー
ポイントの位置を表すアトリビュート。x, y, z の3つの数値。すべてのポイントが必ず持っている。
Nエヌ · Normal
法線。面や点が向いている方向を表すベクトル。ライティングの計算や、押し出す方向の基準に使われる。関連: 法線
Cdシーディー · Color diffuse
色を表すアトリビュート。RGBの3つの数値。color SOP を通すとこれが追加される。
pscaleピースケール
ポイントごとの大きさ。copy to points で形を複製するときに、このアトリビュートで1つずつサイズを変えられる。関連: copy to points
@ptnumアットピーティーナム · point number
ポイントの通し番号（0から始まる）。VEXの中で「何番目の点か」を知るために使う。@ が付く書き方はVEXでのアトリビュート参照。関連: VEX
ディテールアトリビュート / Detail attributeディテールアトリビュート
ジオメトリ全体に1つだけ持たせる値。ポイントごとではなく「この形全体の設定」を渡したいときに使う。グローバルアトリビュートとも呼ばれる。関連: アトリビュート
トポロジ / Topologyトポロジ
ポイントがどうつながって面を作っているか、というつながり方の構造。位置を動かしてもトポロジは変わらないが、分割したり穴を開けると変わる。
法線 / Normalほうせん
面が向いている向きを示す矢印。裏表の判定やライティングに使われる。これが裏返っていると面が真っ黒に見えたり消えたりする。関連: N
UVユーブイ
テクスチャ（画像）を形に貼るための座標。3Dの形を平面に展開した位置を、バーテックスごとに持たせる。関連: バーテックス
バウンディングボックス / Bounding boxバウンディングボックス
ジオメトリ全体がちょうど収まる直方体。大きさや位置の目安として使われ、これを基準に色を付けたり配置したりできる。bbox と略される。
グループ / Groupグループ
ポイントやプリミティブに名前を付けた選択範囲。「この部分だけに処理をかけたい」というときに作る。
ボリューム / Volumeボリューム
空間を格子状に区切って、各マスに値を持たせたデータ。煙や炎のように「面では表せない、中身のあるもの」を扱うのに使う。VDBはその代表的な形式。関連: Pyro
ボクセル / Voxelボクセル
空間を細かい立方体のマス目に区切ったときの、1マスのこと。画像のピクセルを立体にしたもの。ボリュームはボクセルの集まりでできていて、マス目が細かいほど煙の形も細かくなる代わりに計算が重くなる。関連: ボリューム
パックプリミティブ / Packed primitiveパックプリミティブ
中身のジオメトリを1つのプリミティブとしてまとめて持つ仕組み。破片のように同じ形を大量に扱うときに軽くなる。中身を取り出すには unpack を使う。関連: プリミティブ
メッシュ / Meshメッシュ
面がつながってできた形の全体。ポリゴンを網の目のように並べたもの。分割の細かさを「メッシュが細かい／粗い」と言う。関連: ポリゴン / トポロジ
テンプレート / Templateテンプレート
複製のもとになる形。copy to points では、この形が点の数だけコピーされる。向きは、テンプレートの Z 軸が点の N に合わせられる。関連: copy to points / N
HeightField / ハイトフィールドハイトフィールド
地形を「高さの数の並び」として持つ仕組み。面も点も持たず、2次元のボリューム（height）1枚で地形を表す。浸食のような計算ができるのが利点で、レンダする直前にメッシュへ直す（実験034）。
レイヤー / Layerレイヤー
HeightField が重ねて持つボリュームの1枚。最初は height と mask の2枚だが、浸食をかけるとがれき・堆積・流れなどが足されて7枚になる。「どこが削れたか」を色や散布に使える（実験034）。
MPMエムピーエム · Material Point Method
Houdini 21 から入ったソルバ。砂・雪・泥・パンのような「固体と流体の中間」を扱う。物を粒の集まりとして持ち、計算のときだけ格子に移して解く。mpm で始まる SOP が8種、DOP が2種ある（実験061）。関連: ソルバ / シミュレーション
APEXエイペックス
Houdini 20 から入った、リグ（骨組み）を組み立てる仕組み。ノードのネットワークそのものをデータとして持ち歩けるのが特徴で、シーンの中ではなくジオメトリの中に入って流れる。使える部品は 2,220種あり、そのうち 715種は SOP とジオメトリを触るためのもの（実験050）。関連: KineFX / リグ
KineFXキネエフエックス
Houdini で骨組み（スケルトン）とアニメーションを扱う仕組み。骨を「点と線のジオメトリ」として持つので、普通の SOP でそのまま加工できる。kinefx:: で始まる SOP が 133種ある（実験050）。関連: APEX / リグ
リグ / Rigリグ
キャラクターを動かすための骨組みと操作系。手で1点ずつ動かす代わりに、少数の「つまみ」で全身を制御できるようにする仕組み。関連: APEX / KineFX
可変長の入力 / VariadicArgカヘンチョウノニュウリョク
つなぐ数を決めずに、いくつでも受け取れる入力口。APEX の Add はこの形で、枝（サブポート）を生やした数だけ足せる。値を直接入れても無視され、エラーも出ないので気づきにくい（実験050）。関連: APEX
グルーム / Groomグルーム
毛や髪を作って整えること。Houdini では2段構えで、ガイド（案内役、数百本）で形を決め、そこから毛（数万本）に増やす。guide で始まるノードだけで26種ある（実験042・043）。関連: ガイド / clumpid
ガイド / Guideガイド
毛の形を決める案内役の線。実際にレンダされる数万本の毛は、数百本のガイドから増やして作る。ガイド1本は polyline で、どの面から生えたかを示す skinprim をプリミティブに持つ（実験043）。関連: グルーム / skinprim
skinprimスキンプリム
毛やガイドが「土台のどの面から生えたか」を示す番号。グルームのノードはこれが無いと動かない。fur の出力には付かないので、次の工程に渡すには自分でガイドを組む必要がある（実験043）。関連: ガイド / rest
widthウィズ
カーブ（毛や線）の太さを表すアトリビュート。レンダラはこれを見て毛の太さを決める。実測したところ半径ではなく直径だった（実験045）。世界の大きさに対する値なので、小さい土台に既定の 0.001 を使うと画の上で 0.1ピクセルにしかならない。関連: グルーム / アルファ
clumpidクランプID
毛がどの束に属するかを示す番号。hairclump が付ける。種類の数を数えれば束の数が分かり、束ごとに色を変えるといった加工にも使える（実験043）。関連: グルーム
restレスト
点の「元の位置」を覚えておくアトリビュート。形が動いても模様や毛の付き方がついてこないようにするために使う。グルームの土台には必須で、無いと hairgen が止まる（実験043）。VEX の addpoint で作った点は rest が (0,0,0) のまま入り、エラーも出ないまま「原点にあるもの」として扱われる（実験044）。関連: skinprim

よく使う処理

SOPで頻繁に登場する処理。名前が動作をそのまま表しているものが多い。

subdivideサブディバイド
面を細かく分割するノード。分割と同時に形を滑らかにするため、立方体にかけると回数を増やすほど球に近づく。この滑らかにする方式が Catmull-Clark。関連: Catmull-Clark
Catmull-Clarkカトマル・クラーク
面を分割しながら滑らかな曲面に近づけていく計算方式。角が丸まるのが特徴で、「分割したのに形が変わった」と感じる原因はこれ。関連: subdivide
mountainマウンテン
ポイントを法線方向にノイズで押し出して、地形のような凹凸を作るノード。既存のポイントを動かすだけでポイントは増えないため、細かい凹凸を出したいなら先に分割数を上げておく必要がある。関連: ノイズ, subdivide
ノイズ / Noiseノイズ
でたらめに見えて滑らかにつながっている数値のパターン。自然物のばらつきを作るのに使われ、地形、煙、揺れなどほぼすべての「自然に見せたいもの」の元になる。
scatterスキャッター
面の上にポイントをばらまくノード。ばらまいた点にあとから草や岩を複製する、という流れがプロシージャルの定番。関連: copy to points
copy to pointsコピー・トゥ・ポインツ
ポイントの位置1つずつに、別のジオメトリを複製して配置するノード。「100個の岩を並べる」ような作業を1ノードで済ませられる、プロシージャルの中核。関連: scatter, pscale
mergeマージ
複数のジオメトリを1つにまとめるノード。別々に作った形を合流させる合流点として使う。
for-each / フォーイーチフォーイーチ
同じ処理をパーツごとに繰り返す仕組み。Block Begin と Block End という2つのノードで範囲を挟んで作る。「破片1つずつに別々の動きを付ける」など、まとめて処理できないときに使う。関連: イテレーション
イテレーション / Iterationイテレーション
繰り返し処理の1回分。10個のパーツを順に処理するなら、イテレーションは10回ある。「今が何回目か」を数値として取り出して、回ごとに違う結果にすることができる。関連: for-each
wrangleラングル
VEXのコードを直接書き込めるノード。attribute wrangle が代表。ノードを並べるより、数行書いた方が早くて分かりやすい場面で使う。関連: VEX
VEXベックス
Houdini専用のプログラミング言語。ポイント1つ1つに対して同じ計算を一斉に走らせるため非常に速い。`@P.y += 1;` のように短く書ける。関連: wrangle, VOP
polyextrudeポリエクストルード
面を押し出して厚みや突起を作るノード。建物の階や、壁からの出っ張りなどを作るのに使う。
booleanブーリアン
2つの形を足す・引く・重なりを取る、という演算をするノード。四角から円柱を引いて穴を開ける、といった使い方。
voronoi fractureボロノイ・フラクチャー
ジオメトリを細胞のような塊に分割するノード。破壊エフェクトで、壊れる前にあらかじめ破片を作っておくために使う。関連: RBD
浸食 / Erosionしんしょく
水や重力で地形が削れ、削れた土が低いところへ積もること。実験034で測ったところ、4回かけると勾配が32.7%下がり、最高は下がって最低は上がった（山が削れて谷が埋まる）。

シミュレーション

時間を進めながら計算するもの。1フレーム目の結果を使って2フレーム目を計算するため、途中から飛ばして見ることができない。

シミュレーション / Simulationシミュレーション
物理法則にもとづいて動きを計算させること。手で動きを付けるのではなく、条件を与えて結果を計算させる。略してsimとも書く。
ソルバ / Solverソルバ
シミュレーションの計算を担当するノード。剛体用、布用、煙用など対象ごとに専用のソルバがある。
RBDアールビーディー · Rigid Body Dynamics
変形しない硬い物体の物理計算。積み木が崩れる、壁が砕けて飛び散る、といった動きを担当する。関連: voronoi fracture
Vellumベラム
布、ゴム、髪のような柔らかいものを扱うソルバ。比較的軽く扱いやすいため、柔らかいものを試すならまずここから。
Pyroパイロ
煙と炎を扱うソルバ。ボリュームとして計算するため、面のモデリングとは考え方がかなり違う。関連: ボリューム
FLIPフリップ · Fluid-Implicit-Particle
液体を扱うソルバ。液体をパーティクルとして計算し、最後に表面を張って水面にする。
サブステップ / Substepsサブステップ
1フレームの中を何回に分けて計算するかの設定。動きが速すぎて突き抜けてしまうときに増やす。増やすと正確になるが時間もかかる。
キャッシュ / Cacheキャッシュ
計算結果をファイルに保存しておくこと。シミュレーションは重いため、一度計算したら保存して使い回すのが前提。file cache ノードで行う。
フレーム / Frameフレーム
アニメーションの1コマ。24フレームで1秒が一般的。シミュレーションはフレームを順に進めながら計算する。
フラクチャ / Fractureフラクチャ
ひとつの形を破片に割ること。割った時点ではまだ動かない。動かすのはソルバの仕事で、割る工程と動かす工程は分かれている。関連: RBD / voronoi fracture
コンストレイント / Constraintコンストレイント
点と点のつながり方の規則。布なら「この点とこの点は離れすぎない」という条件にあたる。Vellum では規則を作るノードと、それを解くソルバが別になっている。関連: Vellum
スティフネス / Stiffnessスティフネス
伸びにくさ・曲がりにくさ。Vellum では「値 × 10の指数乗」で決まるため、見えている値より指数のほうが効く。実験015で、値と指数を入れ替えた組み合わせが同じ結果になることを確かめた。関連: コンストレイント
ピン / Pinピン
シミュレーション中も動かさないよう固定した点。布の上端を留めて垂らす、といった使い方をする。対象の指定を空にすると「全部が対象」と解釈され、何も動かなくなる。関連: コンストレイント
密度 / Densityみつど
煙の濃さを表す値。ボリュームのマス目ひとつひとつに入っている数値で、全部足したものが煙の総量にあたる。煙のシミュレーションで保存量として測れるのはこれ。関連: ボリューム / ボクセル
散逸 / Dissipationさんいつ
煙を毎フレーム減らす設定。値を d とすると、毎フレーム (1−d) 倍になる。発生源が供給し続ける場合は減り続けるのではなく、やがて 1/d のところで釣り合う。関連: Pyro / 密度
発生源 / Sourceはっせいげん
煙や液体が湧き出してくる場所。ソルバは毎フレーム、ここから新しい分の供給を受け取る。供給が続く限り総量は増え続ける。関連: Pyro / FLIP
パーティクル / Particleパーティクル
位置と速度を持つだけの点。面を持たないので軽く、大量に扱える。火花・雨・砂・群衆のように「小さなものがたくさん動く」表現に使う。液体も内部では粒として計算される。関連: POP / FLIP
narrow band / ナローバンドナローバンド
液体の計算を軽くする仕組み。水面の近くだけを粒で表し、深いところはボリュームで扱う。既定で有効なので、水を深くしても粒の数はほとんど増えない。粒の数を水の量の目安に使いたいときは切る必要がある。関連: FLIP
reseeding / リシードリシード
粒を足したり間引いたりして数を一定に保つ仕組み。名前から「増やすもの」と思いがちだが、実測では切ると40フレームで36%増えた。減らす側も担っている。関連: FLIP / パーティクル
空気抵抗 / Air resistanceくうきていこう
物が空気の中を進むときに受ける、進む向きと逆の力。速さに比例する形（線形抵抗）と、速さの2乗に比例する形（二乗抵抗）がある。Houdini はどちらのソルバでも二乗抵抗だった。POP の popwind の airresist（実験029）も、MPM の mpmsolver の Air Drag（実験066）も、速さの2乗に比例している。MPM のほうは3次元の相対速度の大きさで決まるので、横風が落ちる速さまで変える。
加速度 / Accelerationかそくど
速さが1秒あたりどれだけ増えるか。popforce に 3 と入れると加速度が 3 になり、1秒で速さ3、2秒で速さ6と伸び続ける。上限は無い。
glue / 接着グルー
離れたピースどうしを、近さを頼りにくっつける拘束。Houdini の Vellum では stitch という型の拘束が作られる。力がかかると外れる設定（breaking）が使えるので、「狙った線で破れる」を作るときはここを使う（実験031）。
応力 / Stressおうりょく
拘束1本にどれだけの力がかかっているか。Vellum では拘束のプリミティブに stress として書かれる。ただし solver の normalizestress を切ると値が 566分の1 になるので、数字だけを見るときは設定も一緒に記録する（実験031）。
終端速度 / Terminal velocityしゅうたんそくど
落ちる物が、重力と空気抵抗がつり合って、それ以上速くならなくなる速さ。二乗抵抗なら √(重力 ÷ 抵抗の係数)。MPM の Air Drag を 4.0 にすると式は 1.566046、実測は 1.607434 だった（実験066）。関連: 空気抵抗 / Air resistance
Ground Plane（MPM）グラウンドプレーン
mpmsolver が最初から持っている地面。groundactive が既定で 1 なので、コライダを一つも置かなくても粒は y = 0 で止まる。自由落下を測りたいときは切る（実験066）。関連: MPM / コライダ
Wind Velocity（MPM）ウィンドベロシティ
mpmsolver の風速。ただし風は空気抵抗を通してしか効かないので、Air Drag が既定の 0 のままだと、風速をいくら上げても位置も速度も9桁まで変わらない（実験066）。関連: 空気抵抗 / Air resistance / MPM
クーロン摩擦 / Coulomb frictionクーロンまさつ
「摩擦力は押しつける力に比例し、速さには関係しない」という一番よく使われる摩擦の見立て。止まるまでの距離は 初速² ÷ (2 × μ × 重力)。MPM の Ground Friction はこの μ そのもので、摩擦 0.25 のとき式 3.261978 に対し実測 3.260808 だった（実験067）。ただし摩擦が強いと塊が潰れて、式から外れていく。関連: 摩擦 / MPM
Sticky（MPM）スティッキー
mpmsolver やコライダの粘着。横に滑るぶんにはほとんど効かず（0.5 と 1.0 が6桁まで同じ値）、落として跳ねさせると効く。跳ね返る高さが 0.026922 から 0.013617 へ半分になる。「押しつけている間」ではなく「離れようとした瞬間」に働く数字（実験067）。関連: Ground Plane（MPM） / MPM

実測で覆した情報

ネット上で見かけたが、自分で動かしたら違っていたもの。 このプロジェクトではHoudiniの挙動は実測を正とする方針にしている。

  • 「Apprentice では hython / hbatch が使えない」 誤り

    フォーラム由来の情報として複数箇所で見かけたが、実測では普通に動いた。 Houdini 21.0.700 の Apprentice ライセンスで、GUIがライセンスを保持している状態でも hython を同時起動できた。OpenGL ROP / Karma ROP での headless レンダリングも成功している。 この誤情報を前提にGUI遠隔操作（hrpyc）方式を作りかけて無駄になった。

  • Apprentice ライセンスの入れ直しは hkey ではできない

    License Administrator（hkey.exe）からログインすると 「Installing licenses through hkey is reserved for non-apprentice accounts」と弾かれる。 正解は Houdini 本体を起動し、出てくる「Unable to Acquire a License」ダイアログから進めること。

  • mountain SOP のパラメータ名は roughness / octaves ではない

    実際の名前は rough / oct / lac。 一般的な名前で書くとパラメータが見つからずエラーになる。 ノードのパラメータ名は [p.name() for p in node.parms()] で確認してから使う。
