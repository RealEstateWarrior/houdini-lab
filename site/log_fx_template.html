Vellum クロス — 布で保存されるべき量は何か

/obj/vellum_test  ·  900点の布、4条件 + かたさ掃引

剛体では体積が保たれた（実験014）。布は面なので体積では測れない。代わりに 辺の長さの合計を見る。布は伸びにくい素材なので、たわんでも吊るしても ほぼ変わらないはず。

さらに伸びにくさを下げれば保存が崩れるはず——と考えて試したら、 まったく変化しなかった。原因を追ったら、このの本当の仕組みが分かった。

わかったこと

  • 点数は全フレームで 900 のまま。 布は形が変わるだけで点が増減しない。剛体の体積保存にあたるのが、布ではこの「構造が変わらないこと」。
  • たわませただけでは辺の長さはほとんど変わらない（伸び 0.272%）。自重で垂れるだけでは張力がかからないため。
  • 両端をで留めて吊るすと 0.842% まで増えた。たわむ場合の3.1倍。 指標が張力を捉えられていると確認できた。
  • かたさを 1.0 から 0.02 に下げても結果がまったく変わらなかった。 50分の1にしたのに伸び率は小数点以下5桁まで同じ。
  • 原因は stretchstiffnessexp で、既定値が 10。実効的なかたさは「値 × 10の指数乗」なので、既定は 1.0 × 10¹⁰ という極端に硬い状態。0.02 にしても 2 × 10⁸ でやはり伸びない。
  • 画面に見えている数字だけを触っても実際にはほとんど変わらない。 効くのは指数のほう。布が硬すぎる・柔らかすぎると感じたら、値ではなく指数を疑う。
  • 指数を 0 まで下げると伸び 174%、−6 まで下げると 253% になり、布というよりゴムの挙動になる。
  • ピンの指定でもつまずいた。grouptype の既定はなので、点のを渡すなら points へ切り替える。さらに group を空のままにすると「全部が対象」と解釈され、布全体がピン留めされて一切動かなくなる（最下点が全フレーム 3.0000 のまま、という症状で気づいた）。

Pyro 煙 — dissipation の正体を式で突き止める

/obj/pyro_test  ·  散逸3条件 × 48フレーム

→ この実験の最後に書いた「はボリュームを描けない」は、 実験018で言い過ぎだったと分かった。 同じカメラ・同じ露出で撮り直すと、 も輪郭と厚みによる濃淡は描けている。 描けていないのは、光が中を通ることによる陰影のほう。

剛体は体積、布は辺の長さが保たれた。煙はなので、 測るのはの合計になる。

当初は「煙は消えていくので密度は減るはず」と考えたが、実際には増えた。 が毎フレーム供給し続けるためで、減衰と供給が釣り合う。 そこで釣り合いを式に立てて実測と突き合わせた。

供給が毎フレーム一定で、毎フレーム (1 − d) 倍に減るとすれば、t フレーム後の合計は (1 − (1−d)t) / d 倍になるはず。全フレームで差が 0.0006 以下だった。

わかったこと

  • 当初の予想は外れた。 煙は消えるので減ると思っていたが、供給が続く限り増える。減る量より足される量が多い間は増え続ける。
  • なしのとき、密度の合計はフレーム番号とぴったり同じ比になった（46フレーム目で46.00000倍、差ゼロ）。毎フレーム同じ量が足され一切減らないので当然だが、これがきれいに出ることでが余計なことをしていないと確認できる。
  • dissipation は「毎フレーム (1 − d) 倍に減らす」という意味だと確定した。 この仮定から立てた式と実測の差は全フレームで 0.0006 以下（最大 0.006%）。
  • 行き着く先も式のとおりで 1 / dissipation。0.3 のとき理論値 3.33333 に対し実測 3.33318。
  • この形の検証は応用が効く。の意味が分からないときは、仮定を式にして実測と突き合わせればよい。 説明を読むより確実で、桁が合っているかまで分かる。実験015で「かたさ = 値 × 10の指数乗」を突き止めたのと同じやり方。
  • 構成でつまずいた点。pyrosource は既定で P と pscale しか作らず、density を明示的に追加しないと次のラスタライズが空を返す。しかも pyrosource の attributes は「個数」（数値）、volumerasterizeattributes の attributes は「名前の文字列」で同じ名前なのに意味が違う。
  • ハードウェアレンダラーはボリュームの描画に向いていない。 煙が塊にしか描かれず、濃淡も立ち上りも分からない。ここまでの実験では十分だったが、ボリュームを扱うなら のような本式のレンダラーが要る。

Karma でのレンダリング — ノイズはサンプル数で本当に減るのか

/obj/pyro_test  ·  実験016の煙を、2つのレンダラーで描き比べる

→ ここで使った煙は、実は動いていなかった（実験021で判明）。 そこで 実験024で、立ち上る煙に入れ替えて測り直した。 結果はほとんど同じで、ここの結論はそのまま成り立つ。

実験016で煙を描いたとき、では濃淡が分からないと書いた。 そこで本式のである を使う。 ただ「きれいになった」では終わらせない。

Karma は1ピクセルの色を、乱数で飛ばした何本もの光線の平均で決める。 平均のばらつきは本数の平方根に反比例するはずなので、 数を4倍にすればは半分になるという式が立つ。 外れたら、式か測り方のどちらかが間違っている。

  • 実用的な結論。この場面では32サンプルあたりで費用対効果が折り返す。それ以上は数字を上げても絵は良くならない。詰めたいときは varianceaa_thresh も下げるが、時間は13倍になる。

  • 本当の違いは光が中を通るかどうか。OpenGL は濃さの分だけ暗くするので、どちらから光が当たっているかが絵に出ない。Karma は光源側が明るい。Karma のほうが最も暗い画素が50と薄いのも、光が内部を抜けてくるため。
  • 速さの差は5倍（0.71秒 対 3.64秒）。確認用の描画は今後も OpenGL でよく、Karma は見せる絵に使う。

  • 最初の見立ては外れた。t = 1/airresist で 63.2% になるはずが 75.00%。しかも airresist を4通り変えても 75.00% のまま。1条件で外れただけなら誤差を疑うが、4条件すべてで同じ値が出るのは式が違う証拠である。
  • 正しい式は二乗抵抗だった。dv/dt = airresist × (風速 − v)²。風速3種類×時刻5点の15点すべてで、ずれは 0.0000003 未満。線形抵抗との最大のずれが 2.28 だったのと桁が違う。
  • 式を決められたのは、風速を変えたから。風速3だけで測っていたら、係数が「3」という定数なのか「風速そのもの」なのか区別がつかなかった。1つの設定で合う式は、いくらでも作れてしまう。
  • popaxisforce は既定では何も起きない。効く範囲が「原点を中心とした半径1の球」に決まっている（type / t / r / height）。粒が y=3 にいると範囲の外で、接線速度は 0.0000 のまま位置も動かない。エラーは出ない。
  • 中心と大きさを合わせると回り始めた。接線速度 0.0248 → 1.0126、中心からの距離 0.3669 → 1.0140。回りながら外へ広がる。向きは軸を +Y にしたとき上から見て反時計回り。
  • 粒は点のままではレンダに写らないほど小さい。小さな球を copytopoints で被せて撮った。比較の2枚は出発点を含めた同じ枠で撮っている。枠を別々に取ると「どれだけ進んだか」が画から消える。

実験023で「見立てを断定せずに残しておくと、あとで潰せる」と書いた。 今回はその場で潰せた。外れた見立てを消さずに残したのは、 外れ方そのものが手がかりだったからである。 「airresist を変えても 75.00% から動かない」という事実が無ければ、 誤差を疑って終わっていた。

Vellum の breaking は動く — ただし布の伸びには効かない

/obj/glue  ·  028の宿題。同じ場面で種類だけを変えて決着させる

答えが出た。breaking は動く。ただし効くの種類が決まっている。 glue が作る stitch 拘束はしきい値どおりに破れ、 cloth が作る distance / bend 拘束は同じ場面・同じしきい値でも1本も破れない。

わかったこと

  • breaking は動いていた。stitch 拘束12本が消え、下の布が落ちて最下点が 0.9608 から −8.6439 になった。実験028の「1つも破れない」は、拘束の種類によるものだった。
  • 決め手は、1つのシーンで両方に breaking を入れたこと。消えたのは stitch の12本だけで、distance 770本と bend 682本は1本も消えていない。条件が同じなら、残る違いは種類しかない。
  • しきい値はちゃんと効く。0.000001 と 1.0 では F3 までに全部、10.0 では少しずつ、100.0 以上では1本も破れない。境目は 10 と 100 の間。
  • 028に書いた説明は逆だった。「破れた拘束は broken に入る」ではなく、取り除かれ、グループは空のまま。12本が消えても broken は 0 だった。028では本数も数えていたので結論は変わらないが、理由の説明を訂正した。
  • 素の distance 拘束でも破れない。cloth プリセットのせいではなく、この種類そのものが対象になっていない。
  • DOP レベルでも同じ。breakfrequency を persubstep にしても1本も減らない。判定の頻度の問題ではない。
  • 実用の結論。布を破りたいなら、cloth の拘束を破ろうとしない。破りたい線に沿ってあらかじめ布を切り分け、glue でくっつけておく。あとはしきい値で「どれだけの力で外れるか」を決められる。
  • 道具として2つ。DOP の拘束は dopimport の geodatapath に ConstraintGeometry と書けば取り出せる。もう1つ、normalizestress を切ると stress の値が 7.925 から 0.014 になる（566分の1）。同じ「stress」でも設定によって桁が変わる。

028で「断定はしない」と書いて3つの可能性を残したのが効いた。 そのうち「SOPレベルでは扱われない」は今回否定され（DOPでも同じだった）、 残ったのは「別の条件が要る」。その条件が拘束の種類だと分かった。 021→023 と同じで、見立てを断定せずに残しておくと、あとで潰せる。
