# 実践: Houdini で作る手順（Houdini 研究部）

どの実践も hython で組んで確かめた手順。数字は測った値。hip はサイトから開ける。

## 実践01 地面に物を生やす

でこぼこした地面を作り、その上に200本の木を立てる。プロシージャルモデリングで最もよく使う組み方で、木を岩や草に変えればそのまま応用できる。

- ノードの数: 7個
- かかる時間: 5分ほど
- 元になった実験: 実験008

### 手順1 地面を作る（grid）

平らな格子を1枚出す。大きさを 10×10、分割を 40×40 にした。分割の数がそのまま点の数になり、あとで乗せるでこぼこの細かさの上限を決める。

### 手順2 でこぼこにする（mountain）

地面にノイズで起伏を付ける。height を 0.6、elementsize を 3.0 にした。elementsize は「うねりの大きさ」で、小さくすると細かい岩肌、大きくするとゆるい丘になる。

### 手順3 面の向きを作る（normal）

面がどちらを向いているかを表す N を作る。この段でやるのが肝心で、点だけになってからでは面が無いので計算できない。ここで作っておけば、次でばらまく点が N を受け継ぐ。

### 手順4 点をばらまく（scatter）

地面の上に200個の点を散らす。この点が「木を立てる場所」になる。面積の広いところほど多く置かれるので、傾いた斜面でも自然にばらける。

### 手順5 生やすものを作る（tube）

木の代わりに細い円錐を1本作る。太さを上下で変えて先細りにした。そして回転を X に 90 度かけて、Z 軸方向に倒しておく。理由は次の段で分かる。

### 手順6 点の上に複製する（copy to points）

1本目の入力に円錐、2本目に点をつなぐ。点が持っている N に合わせて、1本ずつ向きが決まる。最後に地面と合流させれば完成。

### 落とし穴

- **テンプレートは Z 軸に伸ばす**: copy to points は、テンプレートの Z 軸を N に合わせる。Y 軸に立ったままの円錐を渡すと、200個すべてが90度倒れる。実験008で200個すべての角度を測ったところ、Y軸のままだと 90.00°、Z軸に倒しておくと 0.00° だった。
- **tube の既定は面ではない**: tube の type は既定が Primitive で、点が1個・面が1枚しか出てこない。複製しても何も見えないので、Polygon に変える。
- **normal は、ばらまく前に**: scatter を通すと面が無くなり点だけになる。そのあとで normal をかけても N は作れない。順番を逆にすると、木が向きを失って全部同じ方向を向く。

## 実践02 地形を作る

平らな板からでこぼこした地面を作る。Houdini で最初に覚えると応用が広い組み方で、岩肌にも雪原にも同じ手順で届く。

- ノードの数: 2個
- かかる時間: 3分ほど
- 元になった実験: 実験003〜007

### 手順1 平らな板を出す（grid）

大きさ 10×10 の格子を出す。まずは分割を 20×20 にしておく。分割の数がそのまま点の数になり、あとで乗せる凹凸の細かさの上限を決める。

### 手順2 ノイズで凹凸を付ける（mountain）

height を 1.2、elementsize を 4.0 にする。height は凹凸の高さ、elementsize はうねりの大きさ。この時点では板がカクカクしている。点が足りないせいで、ノイズの形を表しきれていない。

### 手順3 点を増やす（grid）

分割を 160×160 に上げる。ノイズの設定は何も変えていない。それでも見た目がなめらかになる。凹凸の大きさを決めているのは elementsize で、点の数は「どこまで細かく表せるか」を決めている。

### 手順4 細かさを上げる（mountain）

elementsize を 1.2 に下げ、rough を 0.75 に上げる。elementsize はうねりを細かくし、rough はざらつきを足す。点が足りていれば、ここで岩肌らしくなる。

### 手順5 ノイズの種類を変える（mountain）

basis を worleyFA にする。細胞のような模様のノイズで、削られたような形になる。14種類あり、選ぶだけで見た目が大きく変わる。

### 落とし穴

- **点を増やさずに細かくしても無駄**: elementsize を小さくしても、点が足りなければ表せない。実験004では、重ねるノイズの枚数（oct）を 3 から 8 に増やしても、点が足りない間はまったく変化がなかった。点を増やして初めて効き始める。
- **パラメータ名が思っているものと違う**: roughness や octaves という名前は存在しない。実際の名前は rough / oct / lac。一般的な名前で書くとエラーになる。
- **ノイズを先にかけると、あとの分割でならされる**: 実験003で測ったところ、分割してからノイズをかけると凹凸のずれが最大 0.08062、逆の順だと 0.03671 だった。約2.2倍の差がある。分割は周りの点を平均するので、先に作った凹凸をなめしてしまう。

## 実践03 硬い形を作る（穴を開ける）

機械や建物のような、角のはっきりした形を作る。ここでは箱に円柱で穴を開ける。引く形を変えれば、溝でも窓でも同じ手順で作れる。boolean は見た目で合っているか判断しづらいが、体積の関係式で検算できる。数字はすべて実験012で実測したもの。

- ノードの数: 3個
- かかる時間: 2分ほど
- 検算のずれ: 0.0000049
- 元になった実験: 実験012

### 手順1 土台の箱を出す（box）

大きさ 2.0 × 1.0 × 1.4 の箱を出す。8点・6面のいちばん単純な形。

### 手順2 くり抜く形を作る（tube）

半径 0.32、高さ 3.0 の円柱を作る。箱より高くしておくのが肝で、そうしないと貫通せずに途中で止まる。type は Polygon にする（既定の Primitive だと点が1個しか出ない）。

### 手順3 引き算する（boolean）

1本目の入力に箱、2本目に円柱をつなぎ、booleanop を subtract（差）にする。箱から円柱の形が抜ける。union（和）なら足し算、intersect（積）なら重なった部分だけが残る。

### 手順4 厚みを付けたいときは押し出す（polyextrude）

板から立体を作るときは boolean ではなく polyextrude を使う。dist に入れた距離はそのまま出る（0.5 / 1.0 / 2.0 を指定してできた高さは 0.50000 / 1.00000 / 2.00000、差はゼロ）。inset は各辺から内側に引っ込む距離で、0.3 にすると一辺は両側から 0.6 縮む（10.0 → 9.40000）。パラメータ名は dist / inset / divs で、divisions ではない。

### 落とし穴

- **引く形は貫通させる**: 円柱が箱より短いと、途中で止まった袋小路の穴になる。上下にはみ出す長さにしておくのが確実。
- **結果が正しいかは体積で検算できる**: 実験012で確かめたところ、和と積の合計が元の2つの合計と一致し（差 0.0000049）、差の体積も関係式とちょうど 0 の差で一致した。見た目で判断がつかないときは、この関係式で確かめられる。
- **boolean には8つの演算がある**: よく使う Union（和）/ Intersect（積）/ Subtract（差）のほかに、Shatter（A を砕いて全部の破片を残す）、Seam（境界線だけを出す）、Detect（検出だけして形は変えない）、Resolve（自分自身の重なりを解消する）がある。Shatter の体積は元の箱と完全に一致した（どちらも 8.00000）ので、破壊エフェクトの下ごしらえに使える。Seam は面数 6 のまま体積 0 になる。
- **ポリゴンの球は rows / cols では割れない**: sphere SOP で rows / cols を 30 にしても、面数は 80 のまま変わらなかった。ポリゴン球は多面体を細分する別のやり方で作られている。しかもその粗い球の体積は 9.00180 で、同じ半径の真球 10.30575 より 13% 小さい。ポリゴンで近似した球は必ず内側に寄るので、体積を当てにするなら分割を上げる。

## 実践04 丸くする、角は残す

カクカクした形をなめらかにしたい。でも残したい角もある。この2つを両立させる。

- ノードの数: 3個
- かかる時間: 2分ほど
- 元になった実験: 実験002・011

### 手順1 箱を出す（box）

8点・6面の立方体。ここから始める。

### 手順2 1回だけ分割する（subdivide）

iterations を 1 にする。面が4倍に増えて、角が少し丸まる。1回だけだと、まだ立方体だと分かる形。

### 手順3 3回に増やす（subdivide）

iterations を 3 にすると、面は 64倍の 384枚になり、ほとんど球になる。分割は1回ごとに面を正確に4倍にする。

### 手順4 残したい辺に重みを付ける（crease）

分割の前に crease を挟み、残したい辺に重みを付ける。重み 3 にすると、分割 3回に耐えて角が残る。重みの数字は「何回の分割まで角を保つか」を表す。

### 落とし穴

- **縮む原因は分割ではなく、なめらかにする処理**: 分割すると形が少し小さくなる。実験002で、なめらかにしない方式（Bilinear）で試したところ、1辺は 1.00000 のまま変わらなかった。縮ませているのは分割そのものではなく、同時に走る平滑化のほう。
- **重みが足りているかは、辺の長さだけでは分からない**: 実験011で、重み1のときに1辺の長さだけ見ると角が保たれているように見えた。ところが折れ角を測ると 28.07° まで崩れていた。指標を1つしか見ないと誤判定する。
- **回数を安易に増やさない**: 面は1回ごとに4倍。3回で64倍、6回で4096倍になる。立方体の6面が6回で 24,576面になる。重くなって手が止まるので、必要な分だけにする。

## 実践05 VEX で点を動かす

ノードを並べる代わりに、数行のコードで点を動かす。既存のノードにない動きを作りたいときの逃げ道であり、点数が多いときはいちばん速い手段でもある。ただし「速い」が効くのは点が多いときだけで、その境目も測ってある。数字はすべて実験009・010で実測したもの。

- ノードの数: 3個
- 書くコード: 3行
- 1点あたりの限界コスト: 約1.1ナノ秒
- 元になった実験: 実験009・010

### 手順1 平らな板を出す（grid）

10×10 の格子を 120×120 に分割する。VEX は点1つずつに同じ計算を走らせるので、点が多いほど結果はなめらかになる。

### 手順2 波を作る（attribwrangle）

実行対象（class）を「点ごと」にして、2行書く。1行目で中心からの距離を測り、2行目でその距離から高さを決める。距離で割っているので、外側ほど波が小さくなる。

### 手順3 高さで色を付ける（attribwrangle）

もう1つ置いて、高さから色を作る。Cd は色のアトリビュート。高いところほど赤く、低いところほど青くなる。

### 手順4 実行対象（class）を選ぶ（attribwrangle）

class は5種類ある。Detail (only once) / Primitives / Points / Vertices / Numbers で、既定は Points。同じ @marker = 1.0; というコードでも、Points なら点に、Primitives なら面に、Vertices なら頂点に、Detail ならジオメトリ全体に1つだけ作られる。Numbers だけはアトリビュートが作られない。ジオメトリの要素ではなく、指定した個数の番号に対して走るモードなので、値を書き込む先が無い。

### 落とし穴

- **実行対象で、できるものの置き場所が変わる**: class を「点ごと」にすれば点の属性、「面ごと」にすれば面の属性になる。同じコードでも置き場所が変わるので、あとのノードが見つけられなくなることがある。
- **他のノードの値を読むときは op: を付ける**: パスをそのまま書くと、エラーも警告も出ないまま 0 が返る。頭に op: を付けるのが正しい。気づきにくいので覚えておく。
- **速いが、ループの代わりになるとは限らない**: 実験010で、for-each ループを VEX に書き換えたら 3,969面で 85.9倍速くなった。ただし for-each には「かたまりを切り離す」働きもあり、そこが必要な場合は置き換えられない。速さだけで選ぶと目的を失う。
- **速さを測るのは難しい。三度失敗した**: 一度目：cook(force=True) の前後を時計で挟んだ。計算量を100倍にしても時間は 0.9倍にしかならない。ジオメトリを要求した時点で初めて計算されるので、計測区間の外で処理が走っていた。二度目：Houdini の性能計測機能を使ったが、軽い処理も重い処理も同じ 0.008000 秒を返す。キャッシュが効いていた。三度目：毎回新しいノードを作って初回のクックを測る。これでようやく、計算量100倍の処理が 17.7倍の時間になった。
- **VEX が速いのは、点が多いときだけ**: 64万点に sin×cos を1回かける処理が 2.47ミリ秒、256万点で 4.58ミリ秒。この2点から、1点あたりの限界コストは約1.1ナノ秒（毎秒約9億点）、固定の費用が約1.8ミリ秒と分かる。4万点では 1.49ミリ秒かかっており、そのほとんどが固定費。少ない点数なら、どう書いても体感は変わらない。
- **rand(@ptnum) は毎回同じ値を返す**: 同じコードを別のノードで2回走らせて、全400点が小数点以下9桁まで一致した。乱数といっても点番号から決まる固定の値なので、実行するたびに変わることはない。だから結果が再現するし、逆に「毎回違う値」が欲しいなら種を自分で変える必要がある。

## 実践06 箱を砕いて落とす

硬いものが割れて崩れる。エフェクトで最初に触ると分かりやすい題材で、箱を壁や柱に変えれば、そのまま破壊の表現になる。

- ノードの数: 4個
- かかる時間: 3分ほど
- 元になった実験: 実験014

### 手順1 落とすものを出す（box）

大きさ2倍の箱を、床から少し浮かせた高さに置く。この時点ではただの箱で、8点・6面しかない。

### 手順2 破片に割る（rbdmaterialfracture）

素材に concrete（コンクリート）を選ぶ。素材ごとに割れ方の性質が変わる。ここで割れるのは形だけで、まだ何も動かない。動かすのは次の段。

### 手順3 落とす（rbdbulletsolver）

破片をそのままソルバにつなぎ、床を置く設定を入れる。それだけで重力で落ちる。DOP ネットワークを組む必要はない。

### 手順4 着地させる（rbdbulletsolver）

フレームを進めると床に当たって砕け散る。見えるようにするには unpack を通して中身を取り出す。

### 落とし穴

- **空中では割れない**: 実験014で破片の広がりを測ったところ、落下中はずっと 2.0000 のままで、着地して初めて 5.6408 に広がった。割ってあっても、力がかからなければ割れ目は開かない。
- **体積は完全に保たれる**: 硬いものなので体積は変わらないはず。実測でも全フレームで 8.00000、ばらつき 0.0000000 だった。おかしな結果が出たときは、この量を見ると設定ミスに気づける。
- **床に少し沈む**: 止まった破片は床から約0.022だけ沈んだ位置にある。接触の計算上、完全にゼロにはならない。

## 実践07 布を垂らす

板を布にして、両端を留めて垂らす。旗・カーテン・服の土台になる組み方。

- ノードの数: 5個
- かかる時間: 4分ほど
- 元になった実験: 実験015

### 手順1 布になる板を出す（grid）

4×4 の板を 30×30 に分割する。分割が粗いと折り目がカクカクするので、布として見せるならこのくらいは要る。

### 手順2 留める点を決める（attribwrangle）

VEX を1行書いて、左右の端の点に pins という名前を付ける。ここで名前を付けておくと、あとのノードが「どこを留めるか」をこの名前で指定できる。

### 手順3 布のつながり方を決める（vellumconstraints）

constrainttype を cloth にする。どの点とどの点が、どれくらいの強さで結ばれているかが決まる。続けてもう1つ置き、type を pin、group を pins にして留める。

### 手順4 動かす（vellumsolver）

拘束を作ったノードの出力を2本とも渡す。重力で垂れ始め、しばらくすると形が落ち着く。

### 手順5 落ち着くまで進める（vellumsolver）

フレームを進めると、垂れ方が止まって形が変わらなくなる。

### 落とし穴

- **留める点の指定を空にすると、全部が留まる**: group を空のままにすると「全部が対象」と解釈され、布全体が固定されて一切動かない。実験015では、最下点が全フレーム 3.0000 のままという症状で気づいた。
- **grouptype も切り替える**: grouptype の既定はプリミティブ。点のグループを渡すなら points に変える。変えないと指定が効かない。
- **かたさは「値 × 10の指数乗」**: 見えている数値をいくら触っても布はほとんど変わらない。効いているのは指数のほうで、既定が10になっている。実験015で、値と指数を入れ替えた組み合わせが同じ結果になることを確かめた。硬すぎる・柔らかすぎると感じたら指数を疑う。

## 実践08 煙を出す

球から煙を立ち上らせる。温度を一緒に供給するのが肝で、これを忘れると煙はその場で濃くなるだけで動かない。

- ノードの数: 4個
- かかる時間: 3分ほど
- 元になった実験: 実験016・021

### 手順1 煙の出どころを作る（sphere）

小さな球を下のほうに置く。ここから煙が出る。形は何でもよく、球でも箱でも文字でもよい。

### 手順2 出どころに値を書き込む（pyrosource）

属性の個数を2にして、1つ目に density（濃さ）、2つ目に temperature（温度）を指定する。温度を入れるのがここでの肝。浮力は温度で生まれるので、これがないと煙は昇らない。

### 手順3 ボリュームに変える（volumerasterizeattributes）

点に書き込んだ値を、立体の格子に焼き込む。こちらの属性欄は空白区切りの文字列なので、density temperature と2つ並べて書く。

### 手順4 時間を進める（pyrosolver）

つなぐだけで煙が立ち上る。dissipation を上げると消えやすくなり、disturbance を上げると細かくばらける。

### 手順5 育つまで進める（pyrosolver）

フレームを進めると、頭が広がってキノコ型になる。計算する領域も自動で伸びていく。

### 落とし穴

- **温度を忘れると、煙はまったく動かない**: 実験021で測ったところ、density だけを供給した場合、中身のあるマス目の数が全フレームで 504 のまま、計算領域も 16×32×16 のまま変わらなかった。濃くなるだけで昇りも広がりもしない。温度を足したら、マス目は28倍、領域は縦に4.5倍に伸びた。
- **同じ名前のパラメータで意味が違う**: pyrosource の attributes は「作る属性の個数」で、名前を書く欄ではない。volumerasterizeattributes の attributes は空白区切りの文字列。名前が同じで意味が違うので、片方の書き方でもう片方を埋めると動かない。
- **確認用の描画では煙の陰影が出ない**: OpenGL の描画は速いが、光が煙の中を通る計算をしない。濃淡は出るが、どちらから光が当たっているかは分からない。見せる絵にするときは Karma を使う。

## 実践09 水を落とす

上から水を落として、床にぶつけて広げる。つなぎ方に独特の作法があり、そこさえ越えれば難しくない。

- ノードの数: 5個
- かかる時間: 5分ほど
- 元になった実験: 実験019

### 手順1 水の出どころを作る（box）

小さな箱を上のほうに置く。この形の中から水が湧く。

### 手順2 湧き出し口に変える（flipsource）

箱をつないでボリュームに変える。volumename を source に変えるのを忘れない。既定は surface で、そのままつないでも水は1滴も出ない。

### 手順3 器を作る（flipcontainer）

水を計算する範囲を決める箱。ただの箱ではなく、液体の粒・容器・衝突という3つの筋道を束ねる中継点でもある。

### 手順4 湧き出し口を器に合流させる（merge）

器の1番目の出力と、作った湧き出し口を合流させる。ここで初めて「この器のここから水が出る」という形になる。

### 手順5 解く（flipsolver）

器の3つの出力を、ソルバの3つの入力へそのまま渡す（1番目だけは合流させたほうを渡す）。床を置く設定を入れると、落ちた水が溜まる。

### 落とし穴

- **粒をソルバに直接つないでも動かない**: 実験017で4通りの配線を試して、すべて同じエラーで止まった。器が3つの筋道を束ねる中継点だと気づいていなかったのが原因。粒は器に入れて、器の3出力をソルバの3入力へ渡す。
- **名前が役割を決めている**: 器の1番目の出力を流れているのは粒ではなく、名前の付いた7つのボリューム。source という名前のものだけが水を湧かせる。実測では source で3,588粒、surface や別名では5粒のまま何も起きなかった。
- **粒の数は水の量を表していない**: 既定では水面付近の層だけが粒で表される（narrow band）。水位を上げて量を5倍にしても、粒の数はほとんど変わらない。量の目安に使いたいときは、この設定を切る。
- **粒の間隔は器とソルバで揃える**: 器とソルバの両方に同じ値を入れる。揃っていないと結果が狂う、と付属ヘルプに書いてある。

## 実践10 粒を降らせる

火花・雨・砂のような「小さなものがたくさん動く」表現の土台。ここだけは DOP ネットワークを自分で組む必要がある。

- ノードの数: 6個
- かかる時間: 4分ほど
- 元になった実験: 実験020

### 手順1 粒の出どころを作る（grid）

小さな板を上のほうに置く。この面から粒が生まれる。

### 手順2 DOPネットワークを作る（dopnet）

パーティクルは SOP だけでは組めない。この箱を作って、中に部品を並べていく。

### 手順3 中に3つ並べる（popsolver）

popobject（粒の入れ物）をソルバの1番目、popsource（粒を生む部品）を2番目、popforce（力を加える部品）を3番目につなぐ。popsource には、さっきの板のパスを指定する。

### 手順4 SOP側に取り出す（dopimport）

DOPネットワークの結果は、そのままでは形として使えない。このノードで取り出す。読み込む対象の欄に * を入れるのを忘れない。空だとエラーも出ないまま0点になる。

### 手順5 時間を進める（dopimport）

毎秒200個の指定なら、1フレームあたり約8.3個ずつ増える。重力で落ちながら、下へ長い流れを作る。

### 落とし穴

- **読み込む対象を空にすると0点になる**: 計算自体は動いているのに、SOP側では1点も見えない。エラーも警告も出ないので気づきにくい。* を入れる。
- **位置を式で予測したいなら刻みを細かく**: 実験020で測ったところ、粒は齢より約1.3刻みぶん遅れて落ち始める。刻み（substeps）を倍にすると、ずれは半分になる。見た目だけなら既定で問題ない。

## 実践11 毛を生やして束ねる

球に毛を12,516本生やし、房にまとめて、束ごとに色を変える。毛は Houdini の中でも道具の数が多く（guide で始まるノードだけで24種）、つなぎ方の決まりごとも多い。ここではいちばん短い道を通る。数字はすべて実験042〜046で実測したもの。

- ノードの数: 8個
- かかる時間: 10分ほど
- 出てくる毛: 12,516本
- 元になった実験: 実験042〜046

### 手順1 土台を作る（sphere）

毛を生やす面を1枚出す。type を Polygon Mesh にして、rows / cols を 40×40 にした。既定の Primitive のままだと点も面も無い「式としての球」が出てくるだけで、毛は生えない。この球は 1,522点 / 1,560面 になる。

### 手順2 面の向きを作る（normal）

面がどちらを向いているかを表す N を作る。毛は N の向きに伸びるので、これが無いと向きが決まらない。なお normal SOP が書くのはバーテックスの N で、点の wrangle からは読めない。ここでは次のノードに渡すだけなので問題にならない。

### 手順3 元の位置を覚えさせる（rest）

通すだけで、いまの位置が rest というアトリビュートに焼かれる。グルームの道具は「元の形」を基準に動くので、これが無いと hairgen が「Skin input has no rest attribute.」で止まる。土台をあとで動かすなら、この rest を持ったまま変形させる。

### 手順4 根元をばらまく（scatter）

球の表面に300個の点を散らす。この点がガイド（毛の案内役）の根元になる。面積の広いところほど多く置かれるので、どこかに偏ることはない。

### 手順5 ガイドを組む（attribwrangle）

散らした点1つにつき、外向きに線を1本伸ばす。長さ 0.5 を8等分して9点。ここで2つのアトリビュートを必ず付ける。ひとつは skinprim（どの面から生えたか。xyzdist で調べる）、もうひとつは各点の rest（自分の位置をそのまま入れる）。クラスは「ディテール」にして、1回だけ走らせる。

### 手順6 毛を増やす（hairgen::2.0）

入力0に土台、入力1にガイドをつなぐ。density を 1000、influenceradius を 0.20 にした。density は本数ではなく「面積1あたりの本数」で、面積 12.53039 の球なら 12,516本になる（計算上は 12,530本で、差は 0.1%）。thickness は 0.008 にした。

### 手順7 束ねる（hairclump::2.0）

入力0に毛、入力1に土台をつなぐ。hairgen とは順番が逆なので注意。clumpsize を 0.4 にすると144個の房になり、1房あたり約87本。毛には clumpid という「どの束に属するか」の番号が増える。

### 手順8 束ごとに色を変える（attribwrangle）

プリミティブごとに走らせ、clumpid から乱数で色を作って、その毛の全部の点に Cd を書く。同じ番号なら必ず同じ色になるので、房がそのまま色分けされる。レンダで色を出すときは principledshader の「点の色を使う」を入れておく（既定でオン）。

### 落とし穴

- **つなぐ順番が、2つのノードで逆**: hairgen::2.0 は「土台 → ガイド」、hairclump::2.0 は「毛 → 土台」。片方を覚えてもう片方に当てはめると必ず失敗する。逆につなぐと「Invalid source …」で何も出てこない。実験043で4通りすべてを試して確かめた。node.inputLabels() で読めば、hairgen の入力は Rest Skin / Guides / Animated Skin / Volumes / Guide Interpolation Mesh、hairclump は Guides / Skin / Skin VDB / Custom Clump Curves と出る。
- **wrangle で作った点の rest は (0,0,0) のまま**: addpoint で作った点には、既にあるアトリビュートの欄はできるが中身は既定値のまま入る。土台から rest が流れてきていると、ガイドの全点の rest が原点になる。hairgen は rest の空間で距離を測るので、ガイドは全部が原点にあることになり、1本も使われない。しかもエラーも警告も出ない。見分け方は毛の長さで、unguidedlength の既定 0.05 ちょうどなら1本も拾われていない。
- **influenceradius の既定 0.05 は小さすぎる**: ガイドはこの半径の中にいる毛にしか効かない。半径1の球にガイド300本だと間隔は約0.2なので、既定のままでは 18.9% しか拾われない。0.10 で 73.1%、0.20 で 100%（12,514 / 12,516）。ただし上げすぎると、向きの違うガイドまで平均されて毛が縮む（0.20 で長さ 0.49765、0.80 で 0.48541）。
- **既定の太さ 0.001 は、画の上で 0.1ピクセル**: thickness は毛の直径で、世界の大きさに対する値。半径1の球を画面いっぱいに撮ると 0.103ピクセルにしかならず、ザラついた点の集まりにしか見えない。0.008 まで上げると 0.822ピクセルになり、毛の流れが読める。ただしレンダ時間は 5.0秒 → 10.7秒と倍になる。
- **fur ノードの出力は次の工程に渡せない**: 手軽に毛を出すなら fur ひとつで足りる。ただし fur が出すのは N と P だけで skinprim が無く、hairclump につなぐと「Couldn't find skinprim attribute.」で止まる。束ねたり整えたりするなら、最初からガイドを組む道を通る。

## 実践12 地形を削って草を生やす

HeightField は高さを「数の並び（ボリューム）」として持つ仕組みで、ポリゴンの地形では難しい「水で削る」がそのまま計算できる。削った跡は debris や sediment といったレイヤーとして残るので、そこに草を生やしたり色を塗り分けたりできる。数字はすべて実験034〜037で実測したもの。

- ノードの数: 8個
- かかる時間: 10分ほど
- 地形の解像度: 100×100
- 元になった実験: 実験034〜037

### 手順1 地形の土台を出す（heightfield）

高さを2次元のボリュームとして持つ入れ物を作る。sizex / sizey を 200、gridspacing を 2.0 にした。解像度は size ÷ gridspacing で決まるので、これで 100×100 になる。この段階では面も点も無く、height と mask という2枚のボリュームだけが出てくる。

### 手順2 起伏を足す（heightfield_noise）

mountain と同じ考え方で、高さのボリュームにノイズを足す。amp を 120、elementsize を 80 にした。amp の数字がそのまま高さになるわけではなく、実測では amp 30 で高さの幅が 8.74（約0.29倍）。ただし倍率としては正確で、amp を4通り変えても「幅 ÷ amp」は 0.291329 と小数点以下6桁まで同じだった。

### 手順3 水で削る（heightfield_erode）

山を削って谷に積もらせる。iterations を 4 にした。ここが HeightField を使う一番の理由で、レイヤーが2枚から7枚に増える（debris / sediment / flow / flowdir.x / flowdir.y が追加）。削れた場所・積もった場所・水の流れた向きが、あとから使える形で残る。

### 手順4 メッシュに直す（convertheightfield）

HeightField のままではレンダできないので、最後にこれを通す。マス目1つが点1つになるので、100×100 なら 10,000点 / 9,801面。解像度がそのまま点数になるので、メッシュ化は必要になったところで行う。

### 手順5 面の向きを作る（normal）

あとで草を立てるために N を作る。scatter を通すと面が無くなるので、ばらまく前にやる。

### 手順6 浸食のレイヤーを点に読む（attribwrangle）

volumesample で、点の位置における sediment（積もった量）を読む。ついでに下り坂の向きも作る。高さを2か所サンプリングして差を取るやり方にしているのは、normal SOP が N をバーテックスに書くため、点のラングルから @N を読んでも空になるから。

### 手順7 草を散らす（scatter）

地形の上に900個の点を散らす。ここで読んだレイヤーの値を density に使えば、「削れた場所には生えない」「積もった場所だけ濃くする」といった配り方ができる。

### 手順8 草を複製する（copy to points）

細い円錐を1本作り、点の上に複製する。テンプレートは Z 軸に伸ばしておく（rx に 90 度）。copy to points はテンプレートの Z 軸を点の N に合わせるので、Y 軸のままだと900本すべてが横倒しになる。

### 落とし穴

- **gridsamples では解像度が変わらない**: 名前は「Grid Samples」だが、これを 128 にしても 1024 にしても 100×100 のまま動かない。解像度を決めるのは size ÷ gridspacing。細かくしたいときは gridspacing を下げる。実験034で確かめた。
- **flowdir.x と flowdir.y は入れ替えて使う**: 浸食が残す「水の流れた向き」は flowdir.x と flowdir.y の2枚に分かれている。地形は水平なので、素直に set(fx, 0, fy) と書きたくなるが、これだと下り坂を向かない（実験036で測った平均は 96.5度＝でたらめ）。8通り総当たりで試したところ、入れ替えた set(fy, 0, fx) だけが平均 39.9度まで下がった。
- **normal SOP が書くのはバーテックスの N**: 点のラングルから @N を読んでも空のまま。実験036では、これに気づかず草の向きがでたらめになった。点の N が要るなら、attribpromote でバーテックスから点へ移すか、この手順のように高さから自分で計算する。
- **v@flow という名前は使えない**: convertheightfield はレイヤーを点アトリビュートとして持ってくるので、float の flow がすでに点に乗っている。そこへ v@flow とベクトルで書こうとすると型がぶつかる。実験036でこれに掛かった。名前を変える。
- **浸食の時間は回数に比例しない**: 100×100 で1回 0.68秒、4回 2.35秒。回数を4倍にしても時間は 3.5倍で、準備の分が乗っている。ただし実用の解像度（gridspacing を下げる）ではそのまま重くなるので、形が決まるまでは粗い解像度で試す。

## 実践13 模様を作って貼る

Houdini の中だけで模様の画を作り（Copernicus）、材質に貼る。貼り方は3通りある。色として使う・凸凹に見せる・本当に形を変える。見た目は似ているが、輪郭を見れば区別がつく。数字はすべて実験039〜041で実測したもの。

- ノードの数: 6個
- かかる時間: 10分ほど
- 模様の解像度: 1024×1024
- 元になった実験: 実験039〜041

### 手順1 COP のネットワークを作る（copnet）

画を作るための入れ物。Houdini 21 では Copernicus と呼ばれ、この中で使えるノードは 262種ある。解像度は copnet 側で決める。setres を入れて res1 / res2 に 1024 を入れた。setres を入れ忘れても res1 / res2 の値は使われるので、意図した解像度になっているかは出てきた画で確かめる。

### 手順2 ノイズの画を作る（fractalnoise）

COP ネットワークの中に置く。elementsize が模様の細かさ、rough が「細かい成分をどれだけ残すか」。ここでは elementsize 0.06、rough 0.6 にした。地形の mountain と同じ考え方の数字で、小さくすると細かい岩肌、大きくするとゆるいうねりになる。

### 手順3 画として書き出す（rop_image）

作った画をファイルに落とす。trange を「今のフレームだけ」にして、copoutput に書き出し先を入れ、execute を押す。パスは / 区切りで書く（Windows の \\ をそのまま入れると通らないことがある）。

### 手順4 土台に UV を付ける（uvunwrap）

画を貼るには「面のどこが画のどこにあたるか」の対応（UV）が要る。球をそのまま渡しても UV は付いていないので、uvunwrap を1つ挟む。地形なら convertheightfield が UV を付けて出してくれるので、この段は要らない。

### 手順5 材質を作る（principledshader::2.0）

/mat の中に作る。geo の中には作れないので注意。rough を 0.6 にした。この材質を material SOP で土台に割り当てる。

### 手順6 色として貼る（basecolor_useTexture）

いちばん素直な貼り方。模様がそのまま色になる。形はまったく変わらない。輪郭の長さを測ると、何も貼らない場合との比が 0.99999 で、小数点以下4桁まで同じだった。

### 手順7 凸凹に見せる（baseBumpAndNormal）

光の当たり方だけを変えて、凸凹があるように見せる。enable を入れるだけでは効かず、baseBump_bumpTexture に画を指定する必要がある。実験041では指定を忘れ、何も貼らない場合と数字が完全に一致して気づいた。

### 手順8 本当に形を変える（dispTex）

レンダのときに面そのものを動かす。dispTex_enable を入れ、dispTex_texture に画を、dispTex_scale に動かす量（ここでは 0.12）を入れる。点の数は増えないのに輪郭が変わるのが特徴で、輪郭の比は 1.02873、面積も 1.4% 増えた。

### 落とし穴

- **bump は輪郭を変えない**: これが bump と displacement の違いそのもの。輪郭の長さ ÷ 面積の平方根で測ると、何も貼らない場合を 1.00000 として、色 0.99999 / bump 0.99852 / displacement 1.02873。横から見たときのシルエットに出したいなら displacement しかない。逆に、シルエットが変わると困る場面では bump を選ぶ。
- **トグルを入れただけでは効かない**: bump も displacement も、enable のトグルとテクスチャの指定が別になっている。片方だけだと何も起きず、エラーも出ない。実験041では bump のトグルだけ入れて、何も貼らない場合と数字（点 3,056 / 高さ 2.2916）が完全に一致したことで気づいた。数字が「まったく同じ」なら、それは効いていない印。
- **UV が無いと貼れない**: 球や箱をそのまま渡しても UV は付いていない。貼ったつもりで何も変わらないときは、まず UV があるかを見る。convertheightfield のように、UV を付けて出してくれるノードもある。
- **材質は /mat に作る**: principledshader::2.0 を geo の中に作ろうとすると「Invalid node type name」で止まる。/mat（マテリアルのネットワーク）の中に作って、material SOP からパスで参照する。
- **解像度を上げても画はあまり変わらない**: 実験040で、模様の解像度を 256 から 1024 へ4倍にしても、貼った結果の画の変化は 1.04倍にしかならなかった。細かさは elementsize のほうが効く。まず elementsize で見た目を決めて、解像度は最後に上げる。

## 実践14 骨を入れて動かす

点と線で骨を組み、筒の皮を結び付けて、関節を曲げる。KineFX の骨はただのジオメトリなので、専用のノードを覚えなくても普通の wrangle で作れる。ただし落とし穴が多く、そのほとんどが「エラーが出ないまま間違う」種類のもの。数字はすべて実験051〜054で実測したもの。

- ノードの数: 6個
- かかる時間: 15分ほど
- 曲げても減らない体積: 0.18%
- 元になった実験: 実験051〜054

### 手順1 骨を組む（attribwrangle）

点を3つ置いて、polyline で1本につなぐ。それぞれに name（joint0 / joint1 / joint2）を付ける。これだけで骨になる。KineFX の骨は専用の形式ではなく、点1つが関節1つ、線が親子のつながりを表すだけのジオメトリ。クラスは「ディテール」にして1回だけ走らせる。

### 手順2 足りない属性を埋める（kinefx::rigdoctor）

この時点では P と name しか無い。rigdoctor を通すと localtransform（4×4の行列）・transform（3×3）・parent_idx（親が誰か）の3つが付く。親子関係は線のつながりから読み取られるので、自分で書く必要はない。根元の parent_idx は -1 になる。

### 手順3 関節を回す（kinefx::rigattribwrangle）

普通の attribwrangle と同じ書き方で、関節の行列を書き換える。クラスは「点ごと」。真ん中の関節（joint1）の 4@localtransform に prerotate をかける。回転は子にだけ伝わるので、根元は動かない。

### 手順4 皮を用意する（tube）

骨を包む筒を作る。半径 0.32、高さ 2.0、分割は 60×24。ここでは単純な筒だが、キャラクターのメッシュでも手順は同じ。

### 手順5 皮を骨に結び付ける（kinefx::jointcaptureproximity）

入力は「皮 → 骨」。近さをもとに、点それぞれが「どの骨にどれだけ従うか」を決める。皮に付くのは boneCapture というアトリビュート1つだけで、骨と皮は別々のジオメトリのまま残る。

### 手順6 皮を動かす（kinefx::jointdeform）

入力は3つ。「結び付けた皮 → 元の骨 → 動かした骨」。元の骨と動かした骨を両方渡すのは、その差だけを皮に伝えるため。既定の Linear だと、90度で体積が 27.13% 減る。

### 手順7 痩せないようにする（method）

混ぜ方を Dual Quaternion に変えるだけ。同じ骨・同じ角度で、体積の減りが 27.1284% から 0.1764% になる（154分の1）。速さの差は 41万点で 1.04倍しかないので、ほとんどの場合こちらでよい。

### 落とし穴

- **rigdoctor の3つのトグルは、すべて既定オフ**: そのまま通しても何も足されない。transformations / inittransforms / outputparentidx を入れて初めて属性が出てくる。エラーは出ないので、属性が付いているかを自分で確かめる。
- **rotate と prerotate を取り違えると、関節ごと飛んでいく**: rotate() だと「動かしてから回す」になり、回した関節そのものが原点のまわりを回ってしまう。90度で先端が (−2, 0, 0) に飛び、正しい値 (−1, 1, 0) とのずれは 1.41。30度だと「少し曲がった骨」に見えてしまい、絵では気づけない。大きく振ると差が開くので、確かめるときは90度まで回す。
- **曲げると痩せる。減り方には式がある**: 既定の Linear では、体積の減りが 27.1284% × (1 − cos θ) にぴたり乗る。6通りの角度すべてで、(1 − cos θ) で割った値が 27.1284〜27.1286 にそろった。90度で 27.13%、120度で 40.69%。ねじり（骨の軸まわり）だともっとひどく、179度で 66.81% 減る。
- **痩せる原因は maxinfluences の既定 2**: 1つの点が2本の骨に従うので、関節の近くで2つの行列が混ざる。混ざった結果は、どちらの行列でもない縮んだ位置になる。1 にすると減りは 0.85% まで落ち、根元の点はぴくりとも動かなくなるが、関節が鋭く折れる。3 にするともっと減る（36.84%）。「なめらかにしたいから骨を増やす」は逆効果。
- **「2つの中間」は、属性が無いと動かない**: jointdeform の method を「Blend Dual Quaternion and Linear」にすると「Missing dual quaternion blend attribute」で止まる。点ごとの混ぜ具合を表す float のアトリビュートを自分で作り、名前を dqblendattrib に入れる。全点に 0.5 を入れると、減りは 14.69% で Linear のほぼ半分になった。
- **Dual Quaternion にも癖がある**: ねじれが根元まで広がる。170度ひねったとき、根元の帯は Linear で 14.1度しかねじれないのに、Dual Quaternion では 58.9度ねじれる。さらに、99.2度で止まっている帯のすぐ上が 170度になり、途中に段差ができる。体積は保たれるが、形が素直とは限らない。

## 実践15 塊をぶつけて潰す（MPM）

Houdini 21 から入った MPM は、砂・雪・泥・パンのような「固体と流体の中間」を扱うソルバ。物を粒の集まりとして持ち、計算のときだけ格子に移して解く。組むのは box → mpmcontainer → mpmsource → mpmsolver の4ノードだけで、地面すら置かなくていい。ただし黙って無視されるパラメータが多く、気づかないまま何も起きていないことがある。数字はすべて実験061〜067で実測したもの。

- ノードの数: 6個
- かかる時間: 10分ほど
- 1辺 1.0 の箱の粒: 577個
- 元になった実験: 実験061〜067

### 手順1 落とすものを置く（box）

1辺 1.0 の箱を y = 3.0 に置く。ここはただのジオメトリで、MPM 用の特別な準備は要らない。あとで mpmsource が この中を粒で埋める。

### 手順2 計算する範囲を決める（mpmcontainer）

MPM は粒を格子に移して解くので、その格子が届く範囲を先に決める必要がある。Size と Center で箱を置く。いちばん大事なのは particlesep（粒の間隔）で、これが細かさを決める。0.12 なら 1辺 1.0 の箱が 577粒になる。この範囲は他のノードにも配線でつなぐ。

### 手順3 形を粒に変える（mpmsource）

入力は 0 = 形、1 = さっきの範囲。箱の中が粒で埋まる。粒には Je と Jp（体積がどれだけ変わったか）や v（速度）が付く。横に投げたいときは initialvelocityx に初速を入れる。

### 手順4 解かせる（mpmsolver）

入力は 0 = 源 / 1 = ぶつかるもの / 2 = 範囲。コライダが要らないなら 1 は空のままでよい。地面は最初から y = 0 にあるので、何も置かなくても粒は床で止まる（実験066）。あとはフレームを進めるだけ。

### 手順5 材質を選ぶ（materialtype）

mpmsource の materialtype が本体で、Elastic / Chunky / Liquid / Viscous / Sandy の5つ。既定は Chunky。同じ落とし方でも結果はまるで違い、30フレーム目の高さは Elastic が 1.0462（跳ね返って形が戻っている）、Chunky が 0.6070（潰れたまま）。

### 手順6 地面の摩擦を決める（groundfriction）

mpmsolver の Ground Plane にある groundfriction（既定 1.0）は、高校物理のクーロン摩擦の μ そのもの。横に初速 4.0 で投げたとき、止まるまでの距離は 初速² ÷ (2 μ g) の式に 0.04% で乗る（実験067）。隣の groundsticky は横滑りにはほとんど効かず、跳ね返るときにだけ働く。

### 手順7 粒の間隔を詰める（particlesep）

結果を細かくしたいときは、substep より先にここを疑う。粒を 24.7倍（118個 → 2,916個）に増やしても、時間は 3.73倍にしかならない（実験065）。substep のほうは 16倍にすると時間が 25.5倍かかるうえ、高さはほとんど動かない（実験064）。

### 手順8 粒を面に戻す（mpmsurface）

レンダに回すには面が要る。mpmsurface の outputtype を Polygon Mesh に変える（既定は Surface VDB）。出てくるのは polysoup なので、convert で Polygon に直す。面にすると体積が 27% 太る。膨らむ厚みは粒の間隔の 0.4倍（実験063）。

### 落とし穴

- **materialpreset は、スクリプトから変えても何も起きない**: Material Preset のメニューを10通り全部試して、結果は9桁まで完全に同じだった。エラーも警告も出ない。実際に効くのは materialtypeのほうで、こちらを変えると結果がはっきり変わる（実験062）。理由も確かめた。この項目には recipeutils.setPresetMenu というコールバックが付いていて、UI で触ったときにしか走らない。スクリプトから parm().set() しても、値が入るだけでコールバックは走らない。
- **地面は最初から置いてある**: mpmsolver の Ground Plane は groundactive が既定で 1。コライダを一つも置いていないのに、粒が y ≈ 0.3 で止まって混乱した。自由落下を測りたいときは、これを切る（実験066）。
- **mpmsurface の既定は面ではない**: そのままつなぐと点が2個しか出てこない。outputtype の既定が Surface VDB だから。Polygon Mesh に変えても、出てくるのは プリミティブ1個の polysoup で、体積を測ると 0.06 のような出鱈目な値になる。convert で Polygon に直して初めて正しく測れる（実験063）。
- **風速だけ上げても、粒は流れない**: mpmsolver の Wind Velocity を 0 / 2 / 5 / 10 と上げても、位置も速度も9桁まで完全に同じだった。風は空気抵抗を通してしか効かないので、airdrag が既定の 0 のままだと風速はただの飾り。その airdrag は速さの2乗に比例する抵抗で、しかも3次元の相対速度で決まるため、横風が落ちる速さまで変える（実験066）。
- **substep を上げるのは、たいてい損**: substep を 1 から 16 にすると時間が 25.5倍かかるのに、高さは 0.2998〜0.3048 とほとんど動かない。動くのは横の広がりだけで、それも 8 で落ち着く（実験064）。一方で粒を 24.7倍にすると、時間は 3.73倍で済んで高さが 23% 動く（実験065）。迷ったら粒のほうを細かくする。
- **粒の数は保たれるが、体積は保たれない**: 粒の数は全フレームで幅 0（実験061）。ところが体積は材質しだいで大きく動き、砂は 16% 膨らみ、既定の塊は 31% 縮む（実験062）。砂は見た目にも極端で、同じ箱が 3.4366 × 0.2348 × 3.5088 まで広がる。「体積が保たれているか」を検算に使うと、ここで足をすくわれる。

## 実践16 シミュレーションをキャッシュする

一度計算したシミュレーションをファイルに書き、次からはそれを読む。同じ煙 40フレームが、計算だと約1秒、読むだけなら 0.06秒。

- ノードの数: 5個
- 読む速さ: 計算の約17倍
- 元になった実験: 実験025・027

### 手順1 キャッシュしたいシミュレーションを組む（pyrosolver）

ここでは手順「煙を出す」と同じ4つ（sphere → pyrosource → volumerasterizeattributes → pyrosolver）を使う。このままだと、フレームを動かすたびに最初から計算し直す。40フレーム回すと 0.99〜1.01秒かかった。

### 手順2 下に File Cache をつなぐ（filecache）

solver の下に filecache をつなぎ、表示フラグをこちらに移す。File Path を Explicit にして、Geometry File に $HIP/guide_cache_cache/smoke.$F4.bgeo.sc と書く。$F4 はフレーム番号（0001, 0002 …）に置き換わるので、1フレームが1ファイルになる。$HIP はシーンファイルのあるフォルダ。

### 手順3 書き出す範囲を数値で決める（f1）

Evaluate As を Frame Range にすると、Start/End/Inc の範囲が書き出される。ここの既定は $FSTART / $FEND という式で、シーン全体（新しいシーンなら 1〜240）を指している。40フレームだけ欲しいなら、式を消してから 1 と 40 を入れる（パラメータを右クリック → Delete Channels で式が消える）。

### 手順4 Save to Disk で書き出す（filecache）

Save to Disk を押すと、範囲の全フレームを計算しながらファイルに書く。書き終わったら、フォルダのファイル数を数える。40フレームのつもりなら40個のはず。この手順では 0.15秒で 40個・63.3 MB になった。

### 手順5 Load from Disk で読むほうに切り替える（loadfromdisk）

Load from Disk をオンにすると、上流を計算せずにファイルを読む。40フレーム回すのが 0.99秒から 0.06秒になった。実験025で、読んだ値は計算した値と40フレームすべてで一致する（密度の合計の差 0.0000000000）ことを確かめている。

### 落とし穴

- **範囲に数値を入れたつもりでも、式が残っていた**: 実験025では Python から数値を入れたのに式が残り、40フレームのつもりが 240フレーム書かれた。3,578.9 MB を書いて 28.81秒。式を消してから入れ直すと 63.3 MB・0.15秒で、56倍の無駄だった。書き出したファイルの数を数えれば一発で気づける。
- **上流を変えても、古いファイルを読み続ける**: Load from Disk がオンのままだと、上流のパラメータを変えても画面は変わらない。実験027で pyrosolver の dissipation を半分にしたところ、30フレーム中29フレームで違う値になり、F30 の密度は +52.9%。古いキャッシュを読んでいたら、これを正しい値として使っていたことになる。上流を触ったら書き直す。
- **ファイルを見比べても、正しさは確かめられない**: 同じ計算を2回書き出すと、ファイルの合計サイズが 138バイト違った（38,927,958 → 38,928,096、実験027）。中身の値は同じでも、ファイルはバイト単位では一致しない。確かめるなら、読んだ値そのものを比べる。
- **得をするのは2回目から**: 書き出しが 0.15秒で済んだのは、直前に全フレームを計算していたから。まっさらな状態から書き出せば、計算の時間がそのまま乗る（実験025では 1.17秒）。何度も見返すときや、下流をいじるときに効く。

## 実践17 粒に風を当てる

降ってくる粒を横風で流す。popwind は粒を押し続けるのではなく、風の速さまで追いつかせる。だから流れは途中から一定の速さになる。

- ノードの数: 10個（うち DOP の中に5個）
- 計算の時間: 72フレームで 0.51〜0.65秒
- 元になった実験: 実験020・029

### 手順1 粒の出どころを作る（grid）

1 × 1 の板を y = 3 に置く。この面から粒が生まれる。

### 手順2 DOP ネットワークに粒の部品を置く（popsolver）

手順「粒を降らせる」と同じく dopnet の中に組む。popsolver の入力には名前があり、1番目が Object、2番目が Pre-Solve、3番目が Sources (post-solve)。popobject を1番目に、popsource を3番目につなぐ。popsource には板のパスを入れ、1秒に200個生ませる。

### 手順3 重力を足す（popforce）

popforce の force に (0, −9.80665, 0) を入れる。popforce は入れた数字をそのまま加速度として足し続ける（実験029）。

### 手順4 風を足す（popwind）

popwind を popforce の下につなぎ、それを popsolver の2番目（Pre-Solve）へ。力のノードは数珠つなぎにできる。wind を (3, 0, 0)、airresist を 1 にする。いちばん古い粒の横の速さは、1秒で 2.7978、2秒で 2.9911、3秒で 2.9996。風速の 3 に近づくだけで、超えない。

### 手順5 SOP 側に取り出して、球を被せる（copytopoints）

dopimport で取り出す（読み込む対象に * を入れる）。粒は点なので、そのままではレンダに写らないほど小さい。半径 0.06 の小さな球を作り、copytopoints で粒の位置に配る。

### 手順6 時間を進める（dopimport）

3秒で 602粒。生まれた粒はすぐ風に追いつき、横も下も一定の速さで流れる。そのため流れは曲がらず、まっすぐな斜めの線になる。

### 落とし穴

- **popforce と popwind は、同じ「3」でも別物**: 実験029で、重力なし・最初の1フレームだけ生んだ粒で比べた。popforce に 3 を入れると速さは伸び続け、2.96秒で 8.875。popwind に風速 3 を入れると 2.96秒で 2.6962（風速の 89.87%）で、3 を超えない。「押す」なら popforce、「その速さで流す」なら popwind。
- **風の抵抗は、下向きの動きにもかかる**: この手順では、いちばん古い粒の下向きの速さが 2秒で −2.9338、3秒で −2.9339 と止まった。重力だけなら 3秒で秒速 29 ほどまで加速する計算になる。popwind の空気抵抗は風の向きだけでなく、粒の動き全体にかかる。
- **airresist で追いつく速さが決まる**: 実験029で測ると、popwind の抵抗は速さの差の2乗に比例していた。風速の半分に届くのは 1 ÷（airresist × 風速）秒後。airresist と風速の4通りの組み合わせすべてで 50.00% になった（重力なしの条件）。
- **渦（popaxisforce）は既定のままでは何も起きない**: 効く範囲が、原点を中心とした半径1の球に決まっている。粒が y = 3 にいると範囲の外で、エラーも出ずに1ミリも動かない。中心と大きさを粒に合わせると回り始めた（実験029）。

## 実践18 狙った線で布を破る

Vellum の布は、布そのものの拘束では破れない。破りたい線で先に切っておき、glue で貼り直す。重さが貼り目にかかると、しきい値を超えたところで外れる。

- ノードの数: 11個
- 計算の時間: 40フレームで 3.59秒
- 元になった実験: 実験031・032

### 手順1 布を1枚立てる（grid）

Orientation を XY Plane にして縦に立て、4 × 4、40行 × 40列にする。中心は y = 2.2。1,600点の布になる。

### 手順2 破りたい線で、面に印を付ける（attribwrangle）

Run Over を Primitives にして、面の重心 @P が線より下かどうかを書く。float line = 2.6 + 0.45 * sin(@P.x * 2.2); i@lower = (@P.y < line) ? 1 : 0; 点ではなく面に付けるのが肝心。点に付けると1枚の面の4隅で答えが割れ、切り口がぎざぎざに崩れる。

### 手順3 2枚に切り分ける（blast）

blast を2つ置き、片方は @lower==1、もう片方は @lower==0 を消す。Group Type は Primitives にする。2つを merge で合流させると、切り口の点が二重になる。1,600点が 1,666点（+66）になった。

### 手順4 吊るす場所に印を付ける（attribwrangle）

上端の点をグループにする。if (@P.y > 4.1) { @group_pins = 1; }

### 手順5 布の拘束を作る（vellumconstraints）

Constraint Type を Cloth にする。伸びの distance 4,706本と、曲げの bend 4,420本ができる。ここに breaking を入れても布は破れない（下の「つまずくところ」）。

### 手順6 glue で貼り直す（vellumconstraints）

もう1つ vellumconstraints を置き、左右の出力をそのまま左右の入力につなぐ。Constraint Type を Glue にして、Enable Breaking をオンにして Threshold を 1 にする。重なった点1組につき1本の stitch ができる。今回は 66本で、切って増えた点の数と一致した。ここがずれていたら、貼り忘れか貼りすぎがある。

### 手順7 上端を留める（vellumconstraints）

3つ目の vellumconstraints で Constraint Type を Pin to Target にし、Group Type を Points、グループを pins にする。

### 手順8 解く（vellumsolver）

左右の出力を vellumsolver の左右へ。40フレームの計算は 3.59秒。しきい値 1 だと、66本の stitch は F5 までにすべて外れた。F40 では 683点と 983点の2つの塊に分かれている。

### 落とし穴

- **布の拘束に breaking を入れても、破れない**: 実験031・032で、cloth が作る distance 拘束に breaking を入れ、しきい値を 0.000001 まで下げても1本も減らなかった。breaking が効いたのは glue が作る stitch だけ。だから「先に切って、あとから貼る」順にする。
- **しきい値で、外れるかどうかが決まる**: 実験032では、しきい値 10 以下なら外れ、100 以上なら外れなかった。10 のときは少しずつ外れる。外れないときは、貼り目がまったく見えない。破れるまでは1枚の布として振る舞う。
- **blast の Group Type を間違えると、何も消えない**: 選択肢は上から Guess from Group / Breakpoints / Edges / Points / Primitives。Python で番号の 1 を入れると Breakpoints になり、何も消えずに素通りした。エラーは出ない。実験032では、合流後の点数がちょうど2倍（3,200）になり、stitch が 1,600本できたことで気づいた。切れていない2枚が丸ごと重なっていた。

## 実践19 炎を出して色を付ける

煙の組み方を「燃える元」に変えると炎が出る。温度を blackbody() で色に直せば、低いところは橙、高いところは黄色になる。

- ノードの数: 7個
- 計算の時間: 30フレームで 0.75秒
- 元になった実験: 実験023・026

### 手順1 炎の出どころを置く（sphere）

手順「煙を出す」と同じ小さな球（半径 0.22、y = −0.9、24行 × 24列）。

### 手順2 燃える元を持たせる（pyrosource）

Initialize のメニューから Source Burn を選ぶ。作られる値が burn と temperature になる。burn が「燃える元」で、ソルバがこれを炎に変える。density は作られないことに注意（煙の量を測りたいときは temperature を見る）。

### 手順3 ボリュームに焼き込む（volumerasterizeattributes）

attributes に burn temperature と空白区切りで書く。Voxel Size は 0.05。

### 手順4 炎を出す設定で解く（pyrosolver）

Create Flame Field をオンにすると、燃えている部分の場 flame ができる。煙も出したいなら Set Flame Density をオンにし、Flame Density を 1.0 に上げる（実験023では既定の 0.0001 だとほとんど出なかった）。30フレームの計算は 0.75秒。

### 手順5 中に点をばらまく（pointsfromvolume）

ボリュームそのものには色を付けず、中に点を置いて点に色を付ける。点なら確認用の描画でも色が見える。Point Separation を 0.08 にすると 4,779点になった。

### 手順6 温度を色にする（attribwrangle）

Run Over は Points。2本目の入力にソルバをつなぎ、float t = volumesample(1, "temperature", @P); でその点の温度を読む。vector c = blackbody(t * 3000.0, 6500) / 6500.0; で色にして、@Cd = c / max(max(c.x, c.y), max(c.z, 1e-6)); と一番大きい成分で割る。点の温度は 0.32〜0.99 で、3000倍して 968〜2,979K として色にした。

### 落とし穴

- **blackbody() の答えは 0〜1 ではない**: 引数は2つで、blackbody(温度, 白として扱う温度)。1つだけだとエラーになる。返る値は、2つ目に 6500 を入れると緑がちょうど 6500 になる大きさで、そのまま色に入れると真っ白になる。6500 で割って初めて見える値になった（実験026）。
- **1 で切ると、全部黄色になる**: 1000K は (1.4015, 1.0000, 0.0806)。0〜1 に丸めると (1.0, 1.0, 0.08) で、赤と緑が同じ＝黄色になる。一番大きい成分で割れば (1.0, 0.713, 0.058) で、橙赤のまま明るさだけが揃う。
- **1500K より下は、同じ色になる**: 1000K と 1500K はまったく同じ値だった。赤と青の比は 1000K で 17.39、8000K で 0.7381 と下がっていくが、低いほうは頭打ちになる。炎の一番冷たいところを描き分けたいなら、換算の倍率を上げてこの下限より上に収める。
- **shredding は炎があるときだけ効く**: 煙だけの設定では、shredding を 0 から 5.0 にしても数字が1桁も動かなかった。燃焼を入れると炎がちぎれて薄く広がり、F40 で炎の合計が 40.1% 減った。ただし F5 では温度の合計の差が 0.6% しかない。短いフレームだけ見て「効かない」と決めない（実験023）。
- **冷たい点を消す blast は、ここでは空振りした**: 温度 0.02 未満の点を消す blast も付けたが、ばらまいた点の温度は最低でも 0.32 で、1点も消えなかった（4,779点のまま）。付ける前に、温度の範囲を一度数えておくと無駄な枝を増やさずに済む。

## 実践20 毛を風で揺らす

生やした毛を Vellum で動かし、ソルバの風で横へなびかせる。根元の留め方と、曲がりにくさが何に効くかがつまずきどころ。

- ノードの数: 9個
- 計算の時間: 48フレームで 2.36秒（620本）
- 元になった実験: 実験048・049

### 手順1 毛を生やす面を用意する（sphere）

30行 × 30列の球を作り、normal で向きを付け、rest で元の位置を覚えさせる。毛はこの向きに生える。

### 手順2 ガイドの毛を立てる（attribwrangle）

scatter で根元を 120点ばらまき、wrangle で各点から法線の向きに長さ 0.6・10区切りの線を立てる。線には、どの面のどこから生えたか（skinprim / skinprimuv）を持たせておく。

### 手順3 毛を増やす（hairgen）

hairgen の1番目に面、2番目にガイドをつなぐ。Density 50、Influence Radius 0.25、Thickness 0.012 で 620本・6,820点になった。

### 手順4 根元を留める（attribwrangle）

Run Over を Primitives にして、各毛の最初の点に stopped を立てる。int pts[] = primpoints(0, @primnum); setpointattrib(0, "stopped", pts[0], 1); Vellum はこの値が 1 の点を動かさない。

### 手順5 毛の拘束を作る（vellumconstraints）

Constraint Type を Hair にする。曲げの Stiffness は 0.05。質量を計算する設定（domass）をオンにする。既定はオフで、オフのままだと mass が −1 のまま入る（実験048）。

### 手順6 風を当てて解く（vellumsolver）

左右の出力を vellumsolver の左右へ。Built-in Wind を有効にして、向きを (1, 0, 0)、Built-in Wind Speed を 40 にする。48フレームの計算は 2.36秒。

### 落とし穴

- **Pin to Target では根元が留まらなかった**: 実験048の組み方では、Pin to Target の拘束を足しても1本も作られず、毛が根元ごと落ちた。group・pingroup、pintype の Permanent / Stopped / Soft をすべて試しても同じ。根元の点に stopped を直接立てると効いた。
- **曲がりにくさは、垂れる距離ではなく形に効く**: 曲げの Stiffness を 0 から 1,000,000 まで変えても、毛先の高さは −0.5784 → −0.5852 と 1.2% しか動かなかった。変わったのはまっすぐさで、いちばん曲がった毛で 0.835 → 0.990。固い毛は「同じところまで垂れるが、まっすぐなまま垂れる」。100 あたりで頭打ちになる（実験048）。
- **強い風では毛が伸びる**: 毛の長さは風速 0 で 0.599089、40 で 0.631461 と 5.9% 伸びた（実験049）。重力だけなら 0.63%。Vellum の拘束は硬いばねで、鎖ではない。
- **風の効き方は、粒と同じ二次の抵抗に近い**: 流され具合は、速度の差の2乗で効く式によく乗った（残差の二乗和が一次の式の 3.5分の1）。実験029の粒と同じ形。ただし最大 0.054 ずれ、完全には説明できない。式の違いがはっきり出るのは弱い風のほうで、風速 2 では一次の式が 0.445、二次の式が 0.303、実測は 0.321 だった。

## 実践21 流れの向きに草を寝かせる

浸食した地形には、水が流れた向き（flowdir）が残る。それを草の向きに入れると、草が流れに沿って倒れる。ただし flowdir の x と y は入れ替えて使う。

- ノードの数: 11個
- 計算の時間: 組んで草まで出して 1.72秒
- 元になった実験: 実験034〜036

### 手順1 地形を作って浸食する（heightfield_erode）

heightfield（200 × 200、Grid Spacing 2）→ heightfield_noise（Amplitude 120、Element Size 80）→ heightfield_erode とつなぐ。Iterations per Frame は 4。浸食すると、水が流れた向き flowdir がレイヤーとして残る。

### 手順2 メッシュにする（convertheightfield）

convertheightfield で 10,000点のメッシュにする。このとき flow や sediment などのレイヤーは、点のアトリビュートとして一緒に持ち込まれる。

### 手順3 流れの向きを点に読む（attribwrangle）

Run Over は Points、2番目の入力に浸食後のハイトフィールドをつなぐ。float fx = volumesample(1, "flowdir.x", @P); float fy = volumesample(1, "flowdir.y", @P); v@flowvec = set(fy, 0.0, fx); x と y を入れ替えるのが肝心（下の「つまずくところ」）。名前は flow ではなく flowvec にする。

### 手順4 草の生える場所をばらまく（scatter）

scatter で 900点。ばらまいた点は、元の点のアトリビュート（flowvec）を引き継ぐ。

### 手順5 向きを N に入れる（attribwrangle）

if (length(v@flowvec) > 1e-6) @N = normalize(v@flowvec); else @N = set(0, 1, 0); copytopoints は形の Z 軸を N に合わせる。だから N に流れの向きを入れると、草はその向きへ倒れる。

### 手順6 草の形を作って配る（copytopoints）

tube で根元の半径 0.35・先 0.02・高さ 7 の細い円すいを作り、x に 90度回して Z 軸向きにする（実験008と同じ考え方）。copytopoints で 900点に配り、merge で地形と合わせる。

### 落とし穴

- **flowdir の x と y は入れ替わっている**: flowdir.x を x、flowdir.y を z に入れると、下り坂との角度は平均 96.48度で、でたらめ（90度）とほぼ同じだった。8通りの並べ方を総当たりして、set(fy, 0, fx) だけが平均 39.95度・中央 29.94度まで下がった。他の7通りは 83〜140度（実験036）。
- **同じ名前のアトリビュートとぶつかる**: convertheightfield はレイヤーを点アトリビュートとして持ち込むので、メッシュの時点で flow という数値1つのアトリビュートがある。v@flow と書くとこれとぶつかり、ベクトルのつもりが数値1つになっていた。新しい名前（flowvec）を使う。
- **向きは入れたとおりに正確に向く**: 900本すべてで、N に入れた向きとのずれは 0.000度だった。向きがおかしいときは、複製ではなく N に入れた値のほうを疑う。

## 実践22 動く板で塊を運ぶ（MPM）

MPM の塊を、横に動く板に乗せて運ぶ。コライダは既定では動かない扱いなので、種類を変えないと板をいくら動かしても塊は何も感じない。

- ノードの数: 8個
- 計算の時間: 40フレームで 2.26秒
- 元になった実験: 実験069・070

### 手順1 塊と計算範囲を用意する（mpmsource）

手順「塊をぶつけて潰す（MPM）」と同じく、1辺 1.0 の box を mpmsource で粒にする。mpmcontainer は運ぶ先まで入るよう、Size を (40, 8, 8)、Center を (14, 2, 0) と横長にする。particlesep は 0.12。

### 手順2 板を作って動かす（box）

もう1つ box を (60, 0.4, 6) の板にして、y = −0.2 に置く。Translate の x に式 10.0 + ($FF - 1) / $FPS * 4.0 を入れると、1秒に 4 ずつ横へ動く。

### 手順3 板をコライダにする（mpmcollider）

入力は 0 = 板、1 = 計算範囲。Collider Type を Animated (Rigid) にする。既定の Static のままだと、板を動かしても塊は何も感じない（下の「つまずくところ」）。Friction は 1。

### 手順4 組み込みの地面を切って解く（mpmsolver）

入力は 0 = 粒、1 = コライダ、2 = 計算範囲。ソルバの組み込みの地面（groundactive）はオフにする。自分で置いた床と重なると、先に触った面の摩擦しか効かない（実験069）。40フレームの計算は 2.26秒で、塊の平均位置は x = 5.34 まで運ばれた。

### 落とし穴

- **Collider Type が Static のままだと、何も運ばない**: 実験070で板の速さを5通りに変えても、Static のままでは結果が6桁まで同じだった。エラーも警告も出ない。Animated (Rigid) に変えて初めて塊が動き出す。
- **摩擦 0 の板は、動いていても置き去りにする**: 摩擦 0 では、運ばれた距離も最後の横の速さも −0.000000 だった。板が物を運ぶのは摩擦があるから。
- **追いつくまでは式どおり、追いついた先で遅れる**: 板の速さに追いつくまでは「½ μ g t²」に 0.4% で乗った。追いついたあとは、摩擦が強いほど式より短くなる（摩擦 2.0 で式の 0.88倍）。板が速いほど強くこすられて塊が潰れ（板の速さ 1 → 8 で、高さ 0.49 → 0.25）、上のほうが遅れるため。
- **Compute Velocity は、形が変わる板のときだけ要る**: Animated (Rigid) では、Compute Velocity を切っても値は6桁まで同じだった。Animated (Deforming) で切ると、塊は動かなくなった。剛体の動きなら Rigid と Deforming の答えはほぼ同じ（5.336132 対 5.335937）なので、Rigid でよい。

## 実践23 Karma で見せる絵を撮る

確認は速い OpenGL で、人に見せる1枚は Karma で撮る。材質・ライト・カメラ・Karma の出力ノードの4つを足すだけで撮れるが、白飛びとサンプル数に気をつける。

- 足すノード: 6個
- 撮る時間: 1枚 3.49秒（起動直後の1枚目は 19.49秒）
- 元になった実験: 実験018・024・038

### 手順1 撮るものに色を付けておく（attribwrangle）

ここでは浸食した地形の点に、岩・土・水の3色を @Cd で塗った（堆積 sediment と流れ flow の量で分ける）。点の色は、材質を割り当てなくても Karma に出る。

### 手順2 材質を割り当てる（material）

/mat に principledshader を作り、Use Point Color をオン（既定でオン）、Roughness を 0.75 にする。地形の下に material ノードを足し、Material 欄にその材質のパスを入れる。色のためではなく、白飛びを抑えるために割り当てる（下の「つまずくところ」）。

### 手順3 ライトを置く（envlight）

空全体から照らす envlight（強さ 1.0）と、向きのある hlight を Distant にしたキーライト（強さ 2.4、回転 (−38, −32, 0)）の2つ。点光源は距離で弱まるので、既定の hlight のままだと被写体が暗く写る。

### 手順4 カメラを置く（cam）

cam を置き、解像度を 720 × 460 にして地形が収まる向きに向ける。

### 手順5 Karma の出力ノードで撮る（karma）

/out に karma を作り、Camera にさっきのカメラを入れる。Primary Samples と Max Secondary Samples を 24、Denoiser は off、Output Picture に書き出し先を入れてレンダする。1枚 3.49秒。ただし起動直後の1枚目は 19.49秒かかった。同じ地形を OpenGL で撮ると 1.29秒（実験038）。

### 落とし穴

- **材質が無いと、地形の4割が白く飛ぶ**: 材質を割り当てないと、地形の画素の 43.4% が真っ白に飛んだ。割り当てると 3.1%（実験038）。しかもライトを絞っても直らない。材質ありでキーライトを 2.4 から 0.3 に下げても、白飛びは 3.0% → 2.9% にしか変わらなかった。
- **サンプル数は「上限」で、上げても効かなくなる**: samplesperpixel は「ここまで使ってよい」という上限。64 から 4096 へ64倍にしても、実際に使われたサンプル数は 99 から 567 へ5.7倍にしかならなかった。打ち切りを決めているのは varianceaa_thresh（既定 0.01）。0.0002 まで下げると絵は詰まるが、時間は 5.39秒 → 70.64秒 と13倍になった（実験018）。
- **1枚の時間の多くは、固定費**: 実験018の煙（640 × 360）では、1枚に固定費 2.26秒、1サンプルあたり 7.44ミリ秒。256サンプルでも半分強が固定費だった。軽い絵を何枚も撮るときは、サンプル数より枚数のほうが時間に効く。確認の描画は OpenGL で済ませる。

## 実践24 形を外へ書き出す

作った形をファイルにして、他のソフトへ渡す。Apprentice では FBX・glTF・Alembic が使えないので、形を渡すなら obj になる。画面からは File SOP か ROP Geometry Output で書ける。

- ノードの数: 5個
- 書く時間: 338点の球で 0.003〜0.004秒
- 元になった実験: 実験058・059

### 手順1 渡したい形を用意する（color）

ここでは 16行 × 24列の球に uvunwrap で UV を付け、color で色を塗った。338点・360面で、点に Cd、バーテックスに uv が乗っている。

### 手順2 File SOP で書く（file）

file を下につなぎ、File Mode を Write Files にする。Geometry File に $HIP/guide_export/shape_file.obj と書く。形式は拡張子で決まる。このノードが計算されるたびに、そのときの形がファイルに書かれる。

### 手順3 ROP Geometry Output で書く（rop_geometry）

決まったときに1回だけ書きたいなら、rop_geometry を使う。Output File に $HIP/guide_export/shape_rop.obj、Valid Frame Range を Render Current Frame にして、Save to Disk を押す。Apprentice でも obj は書けた。どちらのやり方でも 48,150バイトで、0.003〜0.004秒。

### 手順4 読み直して確かめる（file）

書いたファイルを File SOP（Read Files）で読み直すと、338点・360面のまま、Cd と uv も残っていた。渡す前に一度読み直して、数と中身を数える。

### 落とし穴

- **FBX・glTF・Alembic は Apprentice では書けない**: FBX は「FBX export is not supported in Houdini Apprentice.」と断られる。glTF と Alembic も同じく止まる。USD は書けるが、拡張子が .usdnc に変えられ、そのままでは他のソフトが読めない。リグやアニメーションを他のソフトへ渡すには、ライセンスを上げるしかない（実験058）。
- **obj では、自分で付けたアトリビュートとグループが消える**: 残るのは位置・色（Cd）・UV（uv）まで。自作の値（myvec・myfloat など）、pscale、点のグループはすべて消えた。バーテックスにあった法線 N は、読み直すと点に移っていた（実験059）。
- **NURBS はポリゴンに刻まれて重くなる**: NURBS の球（312点・1面）は、obj にすると 2,232点・2,160面になった。点が 7.2倍、ファイルは同じ球をポリゴンで作ったときの 17倍（705,418バイト 対 40,409バイト）。NURBS のまま渡そうとしない。
- **stl は線を持てない**: 骨の線（polyline）を含む形を stl にすると、371点が 365点に減った。stl は三角形の集まりしか持てない。Houdini 同士なら bgeo.sc が位置も名前もそのまま往復し、ファイルも最小（6,231バイト）だった（実験058）。

## 実践25 面ごとの繰り返しを VEX に置き換える

「面を1枚ずつ取り出して処理する」は for-each で組めるが、面が多いと重い。点の共有をほどいてから VEX で書けば、同じ結果が数十〜数百倍速く出る。

- ノードの数: 8個（両方のやり方を並べた数）
- 差: 3,969面で約200倍
- 元になった実験: 実験009・010

### 手順1 板を用意して、点の共有をほどく（facet）

10 × 10 の grid の下に facet を置き、Unique Points をオンにする。隣り合う面が共有していた点が面ごとに分かれ、22行 × 22列の板なら 441面・1,764点になる。これをしないと、隣の面が同じ点を別々の高さへ動かそうとして、面ごとに独立して動かせない（実験010）。

### 手順2 for-each で組む場合（block_begin）

block_begin（Method は Extract Piece or Point）と block_end で処理を挟む。block_end は Iteration Method を By Pieces or Points、Piece Elements を Primitives、Gather Method を Merge Each Iteration にし、Piece Block Path に block_begin を入れる。何回目かを知るには、Method を Fetch Metadata にした block_begin をもう1つ置く。

### 手順3 中で1枚ぶんを持ち上げる（attribwrangle）

ループの中の wrangle で int i = detail("op:../each_meta", "iteration", 0); @P.y += rand(i) * 0.5; と書く。取り出した中では @primnum が常に 0 になるので、何枚目かはメタデータから読む。パスの頭の op: を忘れると、エラーも出ずに 0 が返る（実験010）。

### 手順4 同じことを VEX 1つで書く（attribwrangle）

facet の下に wrangle を1つ置き、Run Over を Primitives にする。float h = rand(@primnum) * 0.5; foreach (int pt; primpoints(0, @primnum)) { vector p = point(0, "P", pt); setpointattrib(0, "P", pt, p + set(0, h, 0)); } 各面が自分の点を持ち上げる。for-each と比べると、49面・441面・3,969面のすべてで結果が完全に一致した。

### 手順5 時間を比べる（attribwrangle）

上流を少し動かして計算し直させると、3,969面で for-each は 167ミリ秒、VEX は 0.8ミリ秒だった。for-each は面の数にほぼ比例して遅くなるが、VEX はほとんど変わらない。形を調整するたびにこの差がかかる。

### 落とし穴

- **測り方で差の大きさが変わる**: 実験010ではノードを毎回作り直して測り、3,969面で 191.87ミリ秒 対 2.23ミリ秒（85.9倍）だった。作り直しには VEX の固定費（約1.8ミリ秒、実験009）が乗る。この手順は作ったあとで計算し直させて測ったので、差が約200倍と大きく出た。どちらでも、面が多いほど差が開く向きは同じ。
- **計算し直しを強制しても、されないことがある**: 最初は cook(force=True) で計算し直させて測ったが、VEX 側が 0.02ミリ秒と出た。本当に計算していなかった疑いがあるので、上流の grid をごくわずかに動かして両方を確実に計算し直させ、上流だけの時間を引いて測り直した。
- **for-each が必要なのは、1回分が VEX で書けないとき**: 1回分の処理の中で複数のノードを通したいときなどは、for-each でしか組めない。VEX 1つで書ける処理なら、置き換える価値がある（実験010）。

## 実践26 火花を散らす

1点から一度に粒を飛ばし、重力で落としながら、ばらばらの時刻に消していく。粒を短い線にすると、速さが筋になって火花らしく見える。

- ノードの数: 9個（うち DOP の中に5個）
- 計算の時間: 18フレームで 0.48秒
- 元になった実験: 実験029・079

### 手順1 火花の出どころを1点置く（add）

add で原点に点を1つだけ作る。ここから全部の火花が出る。

### 手順2 一度にまとめて生む（popsource）

dopnet の中に popobject・popsource・popsolver を置く（手順「粒を降らせる」と同じ）。popsource の Emission Type を Points にし、Const. Activation を切って Impulse Activation を入れる。Impulse Count に if($FF == 1, 3000, 0) と書くと、最初のフレームに 3,000粒をまとめて生む。

### 手順3 寿命をばらつかせる（life）

Life Expectancy 1.2、Life Variance 0.6。寿命は 0.6〜1.8 の間に一様に散る（実験079で、4,000粒の寿命を10区間に分けるとどこもほぼ同じ数だった）。生きている数は一定の速さで減っていく。

### 手順4 四方へ飛ばす（velx）

Initial Velocity を Set initial velocity にして、Velocity (0, 3, 0)、Variance (7, 7, 7)。Variance は「その半径の球の中に散らす」数字（実験079）。上向きの速さ 3 より大きい 7 にすると、全方向へ飛び散る。小さくすると上向きの噴水になる。

### 手順5 重力と空気抵抗を足す（popdrag）

popforce に (0, −9.81, 0)、その下に popdrag（Air Resistance 0.15）をつなぎ、popsolver の Pre-Solve へ。popdrag は速さの2乗で効くので、速い粒ほど強く止められる。

### 手順6 ソルバに表示フラグを立てる（popsolver）

DOP の中で popsolver に表示フラグを立てる。立てないと、エラーも出ずに粒が1つも生まれない。そのあと SOP 側で dopimport（読み込む対象に *）で取り出す。

### 手順7 粒を短い線にして色を付ける（attribwrangle）

Run Over を Detail (only once) にした wrangle で、粒ごとに「今の位置 P から P − v × 0.04 まで」の線を作り、元の点は消す。速い粒ほど長い筋になる。色は age ÷ life で黄色から赤へ。計算と線の作成を合わせて、18フレームで 0.48秒。

### 落とし穴

- **ソルバの表示フラグを忘れると、何も起きない**: dopnet は、中で表示フラグの立ったノードまでしか計算しない。立て忘れると粒は1つも生まれず、dopimport に「No DOP object names specified.」という警告が出るだけ（実験079）。
- **All Points では、まとめて生めない**: Emission Type を All Points にすると、Impulse Count に 4,000 を入れても、点1つにつき毎フレーム1粒しか生まれなかった。1点から一度に出すなら Points にする。
- **Variance は箱ではなく球**: Velocity (0, 6, 0)・Variance (3, 3, 3) で、(0, 6, 0) からのずれは最大 2.9999。3 を超える粒は1つもなかった。各成分が ±3 に独立に散る（箱）なら、角の粒は 5.2 まで離れる。
- **空気抵抗は、思ったより強く効く**: 速さの2乗で効くので、速い粒ほど止められる。横に 8 で飛ばすと、airresist 0.5 でも0.5秒後に 2.53 まで落ちた（1秒後 1.55）。この手順では 0.15 にした。

## 実践27 雨を降らせて地面で跳ねさせる

上の板から粒を降らせ続け、地面（groundplane）に当てて小さく跳ねさせる。跳ね方は Bounce で決まり、当たったあとどうするかは Response で決まる。

- ノードの数: 12個（うち DOP の中に6個）
- 計算の時間: 48フレームで 0.51秒
- 元になった実験: 実験079・080

### 手順1 雨雲の板を置く（grid）

8 × 8 の grid を高さ 6 に置く。この面から雨粒が生まれる。

### 手順2 降らせ続ける（popsource）

dopnet の中に popobject（名前を drops にする）・popsource・popsolver を置く。popsource は Emission Type を Scatter onto Surfaces、Const. Birth Rate 1,500、Initial Velocity を Set initial velocity にして Velocity (1, −6, 0)、Variance は 0。Life Expectancy 3。少し横向きの速さを入れると、斜めに降る。

### 手順3 重力を足す（popforce）

popforce に (0, −9.81, 0) を入れ、popsolver の Pre-Solve へ。

### 手順4 地面を置いて merge でつなぐ（groundplane）

groundplane を置き、Bounce を 0.2 にする。merge の1番目に groundplane、2番目に popsolver をつなぎ、merge に表示フラグを立てる。popsolver に置いたままだと、粒は地面をすり抜けて落ちていく（実験080）。

### 手順5 跳ね方を決める（bounce）

Bounce は「跳ね返る速さ ÷ 当たる速さ」なので、跳ね上がる高さは落ちた高さの約 Bounce² 倍（0.5 なら約 0.27倍）。地面と粒（popobject）の Bounce は掛け算になる。粒のほうは既定で 1 なので、地面の値だけ決めればよい。

### 手順6 粒だけを取り出して、線にする（attribwrangle）

dopimport の読み込む対象に drops（粒の名前）を入れる。* だと地面の形まで入ってくる。取り出した粒を、手順「火花を散らす」と同じ wrangle で P から P − v × 0.035 までの短い線にすると、雨の筋に見える。

### 落とし穴

- **高さを半分にしたいのに、Bounce を 0.5 にしてしまう**: 高さ 3 から落とすと、Bounce 0.5 で跳ね上がったのは 0.81（0.27倍）。高さの比は Bounce² に近い（0.25 → 0.071、0.75 → 0.596、1.0 → 1.049）。高さを半分にしたいなら約 0.7。
- **当たったら消したいなら Response**: popsolver の Response を Die にすると、地面に当たった粒は消える（100粒が24フレーム目に0）。Stick は貼り付き、Slide は地面で止まる。既定の Unchanged は跳ね続ける。
- **地面に着いた雨粒は、寿命まで残る**: この手順では 48フレーム目に、3,008粒のうち 2,081粒が高さ 0.5 未満にいた。跳ねたあと地面に溜まっている。気になるなら寿命（Life Expectancy）を短くするか、Response を Die にする。

## 実践28 旗を風になびかせる

縦に立てた布の片側を竿に留め、ソルバの風を横から当てる。風速と布の抵抗で、どれだけ持ち上がるかが決まる。

- ノードの数: 7個
- 計算の時間: 6秒ぶんで 3.6〜4.6秒
- 元になった実験: 実験015・081

### 手順1 旗の布を縦に立てる（grid）

grid を Orientation XY Plane、3 × 2、21行 × 31列にして、左端が x = 0 に来るよう (1.5, 3, 0) に置く。

### 手順2 竿の側に印を付ける（attribwrangle）

if (@P.x < 0.001) i@group_pole = 1; で、左端の点を pole グループにする。

### 手順3 布の拘束を作る（vellumconstraints）

Constraint Type を Cloth。Normal Drag（既定 10）が、風を受ける強さになる。上げると同じ風でもよく持ち上がる。

### 手順4 竿に留める（vellumconstraints）

2つ目の vellumconstraints を Pin to Target にし、Group Type を Points、グループを pole にする。

### 手順5 風を当てて解く（vellumsolver）

vellumsolver の Forces タブで Built-in Wind を有効にし、向きを (1, 0, 0)、Built-in Wind Speed を 4 にする。風速 2 までは旗はほとんど持ち上がらない（85〜78度）。4 で 41度、16 で 9度（0度が水平）。

### 手順6 竿を足して見せる（merge）

細い tube（半径 0.04・高さ 4.4）を竿にして、ソルバの結果と merge する。

### 落とし穴

- **風速を倍にするのは、抵抗を4倍にするのと同じくらい**: 持ち上がり方は「抵抗 × 風速²」でほぼそろった（(風速 4・抵抗 10) 41.1度、(風速 2・抵抗 40) 40.5度）。風の効きは速さの2乗に近い。ただし抵抗がとても小さい (8, 2.5) は 50.5度で、ずれた。
- **1フレームで角度を決めない**: 3秒後の1フレームで測ると、はためきで ±8〜16度ぶれ、抵抗を上げたのに角度が増えるという逆の値まで出た。6秒回して最後の2秒を平均すると、筋の通った値になった（実験081）。見た目を決めるときも、何秒か再生してから判断する。
- **強い風ほど、暴れる**: 風速 16 では角度が −6〜22度の間で揺れ続けた。同じくらい持ち上げるなら、風速を上げるより Normal Drag を上げるほうが揺れは小さかった（風速 8・抵抗 10 で 20度 ±5.6度、風速 4・抵抗 100 で 17度 ±3.1度）。

## 実践29 道に沿って物を並べる

曲線を等間隔に切り、その向きに物をそろえて並べる。坂のある道では、向き（N）だけでなく上（up）も入れないと、物が横に倒れる。

- ノードの数: 8個
- 計算の時間: 0.1秒
- 元になった実験: 実験008・082

### 手順1 道の線を作る（line）

line で長さ 20・400点の直線を x 方向に作り、wrangle で @P.z = 3.0 * sin(@P.x * 0.35); と曲げる。手で描いた curve でもよい。

### 手順2 等間隔に切って、向きを付ける（resample）

resample の Maximum Segment Length を 1.0 にし、Create Tangent Point Attribute をオンにする。各点に道の向き tangentu が付く。Length は上限で、全体を等分する。長さ 25.02 の道なら26等分で、間隔は約 0.96 になる。

### 手順3 向きと上を入れて、両側に振り分ける（attribwrangle）

@N = normalize(v@tangentu); v@up = {0, 1, 0}; up も必ず入れる。道の横向きは normalize(cross(@N, v@up)) で作れるので、同じ点を左右に 1.2 ずつずらして2本にする（addpoint で片側を足す）。

### 手順4 並べる物を作る（box）

杭は 0.15 × 1.0 × 0.5 の box。前後を +Z に向けて作る（copytopoints は形の +Z を N に合わせる）。底が地面に来るよう y に 0.5 上げておく。

### 手順5 点に配る（copytopoints）

copytopoints の左に杭、右に点。Pack and Instance をオンにする。細かい形を1万個配ると、オフでは 714ms・1,878MB、オンでは 2.9ms・4MB だった（実験082）。

### 手順6 道の面を張る（sweep）

sweep に resample の出力をつなぎ、Surface Shape を Ribbon、Width 2、Target Up Vector を Y Axis にする。

### 落とし穴

- **坂のある道で、N だけだと倒れる**: 平らな道なら N だけでも杭はまっすぐ立つ。起伏（高さ ±1.2）を付けると、N だけでは横に最大 49度・平均 19度傾いた。up に (0, 1, 0) を入れると 0.0000度。平らな道で確かめただけでは気づけない（実験082）。
- **間隔がちょうど 1.0 にならない**: resample の Length は「これより長くしない」という上限。道全体を等分するので、1.0 を入れても 0.96 になる。ちょうどの間隔が要るなら、道の長さのほうをその倍数にする。
- **Pack しないと重い**: 2,210点の球を1万個配ると、Pack and Instance オフで点が 2,210万、メモリ 1,878MB、計算 714ms。オンなら 1万点・4MB・2.9ms。形を1つずつ編集しないなら、オンのままでよい。

## 実践30 看板の文字を立体にする

文字の形を作り、厚みを付け、角を丸める。3つのノードでできるが、細かさ・厚み・丸めのつまみは効き方がそれぞれ違う。

- ノードの数: 3個
- 計算の時間: 合わせて 25ms ほど
- 元になった実験: 実験083

### 手順1 文字の形を作る（font）

font の Text に出したい文字を入れる。Font Size が文字の大きさ、Level of Detail は曲線の刻みの細かさで、大きさは変わらない。1（既定）で「SP」が 962点、4 にすると 3,626点。曲がった文字を大きく写すときだけ上げる。

### 手順2 厚みを付ける（polyextrude）

polyextrude の Distance に厚みを入れる。入れた値がそのまま奥行きになる（0.15 → 0.150000）。Output Back は入れたままにする。切ると裏のふたが消えて、裏から見ると穴が開く。

### 手順3 角を丸める（polybevel）

polybevel の Distance で角を丸める。文字の太さに対して 0.01〜0.04 くらいが使いやすい。上げすぎても、ある値から先は形が変わらない（この文字では 0.08 以上で同じ）。Divisions を上げると丸みが滑らかになる。

### 落とし穴

- **丸めを強くしても、途中から効かない**: polybevel の Distance を 0.08 / 0.15 / 0.3 にしても、面積は 1.616047 で6桁まで同じだった。ぶつかったら止める設定（Detect Collisions・Stop Loops）が既定で入っていて、細い部分の幅より大きくは丸められない。エラーは出ないので、効いていないことに気づきにくい（実験083）。
- **丸めは、点や面の数では確かめられない**: Distance を 0 から 0.3 まで変えても 5,776点・5,778面のまま。効いているかどうかは、見た目か面積（measure SOP）で確かめる。
- **Level of Detail を上げても、文字は大きくならない**: 0.2 でも 4 でも、幅 1.1220・高さ 0.7390 で同じ。変わるのは点の数だけ（222 → 3,626）。大きさを変えるのは Font Size。

## 実践31 ドミノを倒す

板を等間隔に並べ、最初の1枚だけを押す。あとは当たって倒れていく。間隔は板の高さの 0.25〜1.03倍に収める。

- ノードの数: 5個
- 計算の時間: 12枚・160フレームで 0.5秒
- 元になった実験: 実験014・084

### 手順1 並べる場所を作る（line）

line で、並べたい間隔 × (枚数 − 1) の長さの線を作り、点を枚数ぶん置く。高さの半分（ここでは y = 0.3）に上げておくと、板の中心がそろう。

### 手順2 板を1枚作る（box）

box を 厚み 0.08 × 高さ 0.6 × 幅 0.3 にする。間隔は、この高さを基準に決める（下の「つまずくところ」）。

### 手順3 点に配る（copytopoints）

copytopoints で板を点に配り、Pack and Instance をオンにする。1枚が1つの塊になり、剛体として扱える。

### 手順4 最初の1枚を押す（attribwrangle）

Run Over を Primitives にして、最初の塊の点に初速を書く。int pts[] = primpoints(0, @primnum); setpointattrib(0, "v", pts[0], (@primnum == 0) ? set(1.6, 0, 0) : set(0, 0, 0)); プリミティブに v@v と書いても効かない。

### 手順5 解く（rbdbulletsolver）

rbdbulletsolver につなぎ、Ground Plane を有効にする。12枚なら 160フレームで 0.5秒ほど。フレーム数は多めに取る。間隔が広いと倒れきるまでに5秒以上かかる。

### 落とし穴

- **初速をプリミティブに付けても倒れない**: packed の塊に v@v を書いても、rbdbulletsolver は動かさなかった。エラーも警告も出ない。点に setpointattrib で書くと動く（実験084）。
- **間隔は、板の高さの 0.25〜1.03倍**: 高さ 0.6 の板で、間隔 0.15（0.25倍）だと12枚中3枚で止まり、0.66（1.10倍）だと2枚で止まった。詰めすぎても、空けすぎても倒れない。倒れる列の進む速さも変わり、間隔 0.25 で1秒に 10.56枚、0.62 で 2.05枚（実験084）。
- **フレームが足りないと「止まった」に見える**: 96フレームで打ち切ると、24枚や広い間隔が途中で止まったように見えた。160フレームまで伸ばすと最後まで倒れた。止まったのか続いているのかは、最後のフレームの傾きで分かる（止まったものは 0〜12度、倒れたものは 74度以上）。

## 実践32 壁を崩す

壁を破片に割り、球をぶつけて崩す。割るのは1つのノードでできるが、破片をつなぐ「強さ」の決め方でほとんど決まる。強すぎれば壊れず、弱すぎれば当てる前に崩れる。

- ノードの数: 6個
- 計算の時間: 割る 1.1秒＋解く 0.3〜1.2秒
- 元になった実験: 実験014・085

### 手順1 壁を作る（box）

box を 3 × 2 × 0.25 にして、下端が地面に来るよう y = 1 に上げる。

### 手順2 破片に割る（rbdmaterialfracture）

rbdmaterialfracture の Material Type を Concrete にし、Fracture Level 1、Scatter Points に破片の数を入れる。指定した数がそのまま破片の数になる（25 → 25個・216面）。割る時間は 10個でも 200個でも 1.1〜1.3秒とほぼ同じ。

### 手順3 壊れる強さを決める（concrete_primarystrength）

Primary Strength が、破片どうしをつなぐ力。既定のままでは、球をぶつけても壊れない。この壁では 500 前後が使える値で、700 だと1個しか外れず、100 まで下げると球を当てなくても自分の重さで崩れた。

### 手順4 ぶつける球を作る（attribwrangle）

球に s@name = "ball"; で名前を付け、別の wrangle（Run Over は Points）で v@v = set(12, 0, 0); と初速を入れる。packed にして混ぜると、球だけが動いて壁は反応しない。破片と同じ「name で区切られたポリゴン」の形にそろえる。

### 手順5 解く（rbdbulletsolver）

壁の破片と球を merge して rbdbulletsolver の1番目へ。2番目には rbdmaterialfracture の2番目の出力（拘束）をつなぐ。Ground Plane を有効にする。60フレームで 0.3秒（破片25個）〜1.2秒（200個）。

### 落とし穴

- **崩れたのは球のせいとは限らない**: 強さ 100 では、球を当てなくても（速さ 0）15個の破片が動いた。壁が自分の重さを支えられていない。崩れ方を見るときは、まず球を当てない場合を1回流す。
- **強さ 10 より下は、つないでいないのと同じ**: 10 / 1 / 0 の結果が、動いた破片15個・いちばん動いた距離 2.439 まで完全に一致した。下げれば下げるほど崩れるわけではない。
- **破片を増やすと、崩れる範囲も広がる**: 同じ強さ・同じ球で、動いた破片の割合は 3/10 → 16/25 → 42/50 → 85/100 → 179/200。細かくすると崩れやすくなるので、破片の数を変えたら強さも決め直す。

## 実践33 葉を風で舞わせる

落ちてくる粒を横風で流し、風の乱れでばらけさせる。粒に小さな板を配って進む向きに合わせると、葉が舞っているように見える。

- ノードの数: 10個（うち DOP の中に5個）
- 計算の時間: 602枚・72フレームで 0.43秒
- 元になった実験: 実験029・086

### 手順1 葉が生まれる場所を置く（grid）

1 × 2 の grid を Orientation ZX Plane にして、高さ 2.5 に置く。この面から葉が降ってくる。

### 手順2 粒を生み続ける（popsource）

dopnet の中に popobject・popsource・popsolver。popsource は Emission Type を Scatter onto Surfaces、Const. Birth Rate 200、Life Expectancy 8、Variance は 0.2 ほど。

### 手順3 弱い重力を足す（popforce）

葉は軽いので、popforce は (0, −2, 0) くらいにする。9.81 のままだと、舞う前に落ちてしまう。

### 手順4 風と乱れを入れる（popwind）

popwind の Wind を (2, 0, 0)、Air Resistance 2。Noise の Amplitude が乱れの強さ、Swirl Size が渦の大きさ。Amplitude 2 で散らばりが 0.76 → 0.85、4 で 1.47 に広がる（実験086）。

### 手順5 葉の板を進む向きに配る（copytopoints）

dopimport で取り出し、wrangle（Run Over は Points）で @N = normalize(v@v); v@up = {0,1,0};。0.12 × 0.07 の grid を copytopoints（Pack and Instance オン）で配る。

### 落とし穴

- **小さい乱れは、入れても見た目が変わらない**: Amplitude 0.5 / 1 の散らばりは 0.7303 / 0.6574 で、乱れ 0 の 0.7621 と変わらない（むしろ小さい）。落ち方のばらつきに埋もれてしまう。変化が欲しいなら 2 以上から（実験086）。
- **乱れは、速さも上げる**: Amplitude 0 → 4 で、粒の速さの平均が 1.882 → 3.588 になった。舞わせるつもりで上げると、思ったより遠くまで飛ぶ。
- **渦の大きさで「細かい揺れ」と「流れ」が変わる**: Swirl Size 0.5 は細かく揺らすだけ（x の平均 2.648）、8 は流れごと運ぶ（3.254）。同じ Amplitude でも見え方が違う。

## 実践34 ターンテーブルで1周見せる

作ったものを回して、1周ぐるりと見せる。物を回すか、カメラを回すかの2通りがあるが、形は同じで、変わるのは光の当たり方。

- 足すノード: 2個（中心寄せと回転）
- 撮る時間: 1コマ 13〜30ms・24コマで 0.3〜0.7秒
- 元になった実験: 実験083・087

### 手順1 見せるものを用意する（font）

ここでは手順「看板の文字を立体にする」で作った立体文字を使う。何でもよい。

### 手順2 中心を原点に寄せる（xform）

xform で、外接箱の真ん中が原点に来るようにずらす。ずらす量は当て推量にしない。ずれていると、回すたびに画の中で位置が動く（実験087）。

### 手順3 回す（xform）

もう1つ xform を足し、Rotate の y に式 ($FF - 1) / 24.0 * 360.0 を入れる。24フレームで1周。コマ数を増やしたいなら 24 を変える。

### 手順4 1周ぶんを書き出す（xform）

1コマずつ画像に書き出す。320 × 320 なら1コマ 13ms、720 × 720 でも 30ms。24コマの1周で 0.3〜0.7秒。そのあと GIF にまとめると、PNG 合計の半分弱の大きさ（320 × 320・24コマで 129KB）。

### 落とし穴

- **カメラを回すと、裏側が暗くなる**: ライトは世界に固定されているので、カメラだけ回すと影の側へ回り込む。写っている部分の明るさの平均は、物を回すと 176〜186 で一定、カメラを回すと 186 → 51 まで落ちた。形（シルエット）は 0.01ポイントまで同じ（実験087）。見せるだけなら物を回すほうが安定する。
- **中心がずれていると、回転で位置が動く**: ずらす量を当て推量で入れたとき、同じ角度なのに画面に占める割合が 14.11% と 5.37% に食い違った。外接箱の真ん中を測って原点に寄せると一致した。
- **1枚目は遅い**: 320 × 320 の最初の12コマだけ、1コマ 75ms だった（2回目以降は 13ms）。下ごしらえの時間が1回目に乗る。速さを比べるときは1回目を捨てる。

## 実践35 文字を光らせる

材質に発光を入れて、看板の文字のように光らせる。強くするほど明るくなるわけではなく、増えるのは周りへこぼれる光と、撮る時間。

- 足すノード: 3個（材質2つと割り当て）
- 撮る時間: 1枚 3.4〜12.4秒（発光の強さによる）
- 元になった実験: 実験038・088

### 手順1 光らせる物と、床を用意する（grid）

立体文字（手順「看板の文字を立体にする」）を床の grid の上に立てる。こぼれる光は床で見えるので、床があると分かりやすい。

### 手順2 発光する材質を作る（principledshader）

/mat に principledshader を作り、Emission Color に光らせたい色、Emission Intensity に 4〜16 を入れる。Base Color は暗めにしておくと、光っている部分がはっきりする。

### 手順3 材質を割り当てる（material）

material ノードで、文字には発光の材質、床にはふつうの材質を割り当てる（実験038）。

### 手順4 Karma で撮る（karma）

ライトは弱めのドーム（0.12）だけにして、発光の色が分かるようにする。640 × 400・サンプル24 で、1枚 3.8〜12.4秒。

### 落とし穴

- **強くしても、文字自体は明るくならない**: Emission 16 → 64 で、文字の明るさは 98.64 → 100.39（+1.8%）。画素は 255 で止まるので、増えるのは白く飛ぶ面積だけ（4.42% → 4.74%）。「もっと光らせたい」ときに変わるのは、周りの明るさ（床 126.95 → 143.07）。
- **発光は重い**: 同じ絵で、Emission 0 が 3.79秒、64 が 12.35秒（3.3倍）。ライトを1つ足したのと同じくらいかかる（実験088）。
- **まわりを照らさなくてよいなら、切ると3倍速い**: Emission Illuminates Objects を切ると、床の明るさが発光0のときと同じ 96.89 に戻り、文字は光ったまま。撮る時間は 10.27秒 → 3.40秒。看板の文字のように「光って見えればよい」ならこれでよい。

## 実践36 落ち葉を地面に積もらせる

舞わせた葉を地面に当てて、その場で止める。止まるかどうかは摩擦ではなく、当たったあとの振る舞い（Response）で決まる。

- ノードの数: 13個（うち DOP の中に6個）
- 計算の時間: 400枚・144フレームで 0.7秒
- 元になった実験: 実験080・086・089

### 手順1 舞う葉を作る（popwind）

手順「葉を風で舞わせる」と同じ組み方（弱い重力・風・乱れ）。ここでは風 (1, 0, 0)、Amplitude 2。

### 手順2 降らせるのを途中で止める（popsource）

Const. Activation に $FF <= 48 と書いて、最初の2秒だけ降らせる。降らせ続けると、いつまでも積もらない（4秒間降らせ続けたときは、801枚中 69枚しか地面に来なかった）。

### 手順3 地面を足す（groundplane）

groundplane を置き、merge の1番目につないでmerge に表示フラグを立てる（手順「雨を降らせて地面で跳ねさせる」と同じ）。Bounce は 0.1 くらい。

### 手順4 当たったら止める（popsolver）

popsolver の Response を Stick にする。400枚のうち 180枚が地面で止まった。既定（Unchanged）では 20枚、Slide では 0枚（実験089）。

### 手順5 葉を配って見せる（copytopoints）

取り出した粒に 0.16 × 0.10 の板を配る（向きは v から）。風下まで床を広げておく。風で流された葉が、床の外に出てしまう。

### 落とし穴

- **摩擦を上げても止まらない**: 地面の Friction を 0 / 0.5 / 1 と上げても、止まった葉は 0 / 4 / 20枚。摩擦は横滑りを遅くするだけで、跳ねと風で動き続ける。止めたいなら Response を Stick にする（実験089）。
- **Slide は止まらないうえに重い**: Slide では止まった葉が 0枚。計算も 1.63秒で、Unchanged（0.63秒）の 2.6倍かかった。
- **降らせ続けると積もらない**: ずっと降らせていると、地面にあるぶんより空中のぶんが多くなる。積もった絵が欲しいなら、降らせる時間を区切って、そのあとも数秒回す。

## 実践37 岩を作る

球を割ったかけらに、うねりと細かいでこぼこを重ねると岩になる。割れた平らな面が岩らしさの元。でこぼこを乗せる前に、網を細かく均等にしておく。

- 足すノード: 10個
- 点の数: 7,321
- 仕上がりを撮る時間: 11.4秒（Karma 1280×720）

### 手順1 もとの形を置く（sphere）

sphere を置き、Primitive Type を Polygon Mesh、半径を 0.9 × 0.6 × 0.75 にする。これを割って、その1かけらを岩にする。

### 手順2 割る位置を散らす（scatter）

scatter で表面に9個の点をばらまく。点の1つ1つが、割れたかけらの中心になる。点を増やすほど、かけらは小さく、面の数は多くなる。

### 手順3 球を割る（voronoifracture）

voronoifracture の左に球、右に点をつなぐ。球が点の数だけのかけらに割れ、割れ目は平らな面になる。この平らな面と角が、岩らしさの元になる。

### 手順4 かけらを1つ取り出す（matchsize）

blast の Group に @name=piece4 と書き、Delete Non Selected を入れると、そのかけらだけが残る。matchsize で真ん中に寄せ、底を床の高さにそろえる。

### 手順5 網を細かく均等にする（remesh）

remesh で三角形の網に作り直す。Target Size を 0.02 にすると、どこも同じくらいの大きさの三角形で埋まる。このあと乗せるでこぼこは、点を動かして作るので、点が少ない所は細かく動けない。

### 手順6 大きなうねりを乗せる（mountain）

mountain で面を法線の向きに押し出す。Height 0.12・Element Size 0.6。割れ面の平らさを残したいので、うねりは控えめにする。Height を上げすぎると、割れ面が溶けて芋のようになる。

### 手順7 細かいでこぼこを重ねる（mountain）

もう1つ mountain をつなぎ、Height 0.035・Element Size 0.1 にする。大きさの違うノイズを2段に分けると、遠目の形と近くで見た肌理を別々に調整できる。

### 手順8 色のむらを付ける（attribwrangle）

attribwrangle に2行だけ書き、色（Cd）の明るさを 0.35〜1.0 でばらつかせる。大きな模様（×9）と細かい模様（×38）を混ぜると、同じ灰色でも汚れや風化のようなむらになり、作り物っぽさが消える。float n = noise(@P * 9.0) * 0.6 + noise(@P * 38.0) * 0.4;@Cd = fit(n, 0.25, 0.75, 0.35, 1.0);

### 手順9 岩の材質を当てる（material）

/mat に principledshader を作り、Base Color を少し茶色がかった灰色、Roughness 0.82 にする。Use Point Color を入れると、前の段の色のむらが材質に乗る。material ノードで割り当てる。

### 落とし穴

- **remesh を省くと、でこぼこが乗らない**: かけらのままでは 264 点しかなく、mountain は点を動かすだけなので、細かい肌理が乗らない。remesh の Target Size を 0.08・0.04・0.02 にすると点は 452・1,804・7,321 個。細かいでこぼこ（Element Size 0.1）をはっきり出すには、その 1/5 くらいの 0.02 が目安。
- **網を細かくすると、そのぶん重くなる**: mountain 2つまで計算し直す時間は、0.08 で 0.01 秒、0.02 で 0.12 秒。岩をたくさん並べるなら、1つを細かく作ってから複製する（手順「地面に物を生やす」）。

## 実践38 ネオン管の看板を作る

文字の輪郭を1本の線として取り出し、その線に沿って細い管を通す。光る材質を当てるだけで、夜の看板になる。形は2ノード、光は材質1つ。

- 足すノード: 6個（形は2個）
- 管の面の数: 11,376
- 仕上がりを撮る時間: 97.9秒（Karma 1280×720）

### 手順1 文字を置く（font）

font に文字を打ち、Type を Polygons Only、Hole Faces を切る。入れたままだと O の内側と外側が1本の線でつながり、管にその線が出る。文字は面（塗りつぶした形）として出てくるが、ほしいのはその輪郭の線。

### 手順2 線に沿って管を通す（sweep）

sweep の Surface Shape を Round Tube、Radius を 0.018 にする。文字の面をそのままつなぐと、面の縁（輪郭）に沿って細い筒ができる。曲がったところには font がもともと細かく点を置いているので、並べ直しは要らない。Columns は筒の周りの分割数で、12 あれば丸く見える。

### 手順3 取り付ける板を置く（box）

管の後ろに box で薄い板を置く（文字より上下左右に少し大きく、厚み 0.04）。光が板に広がるので、看板らしく見える。

### 手順4 光る材質を当てる（merge）

principledshader を2つ作る。管には Emission Color をピンク、Emission Intensity を 9。板は Base Color をほぼ黒、Reflectivity 0.5 にして、光が映り込むようにする。material で割り当て、merge でまとめる。

### 落とし穴

- **Hole Faces を入れたままだと、O に余計な線が出る**: font の Hole Faces（既定で入）は、O や A の穴を外側の輪郭と1本の線でつないで1つの面にする。その面の縁に管を通すと、つないだ線にも管ができ、O の上に縦の線が1本見えた。切ると外側と内側が別々の輪郭になり、線は消える。
- **Columns を増やしても、見た目はほとんど変わらない**: 管の周りの分割（Columns）を 4・12・32 にすると、面の数は 3,792・11,376・30,336。管が細いので、12 を超えると画ではほぼ見分けられない。重くしたくなければ 8〜12。
- **ビューポートでは光らない**: 発光はレンダラー（Karma）が計算するもので、ビューポートでは色が付くだけ。光り具合は Karma で撮って確かめる。

## 実践39 宝石を散らす

分割の少ない球を平らな面に分けるだけで、宝石のカットになる。色と大きさを1つずつ変えて散らし、光を通す材質を当てれば、光が中で屈折してきらめく。

- 足すノード: 7個
- 宝石1つの面: 40枚
- 仕上がりを撮る時間: 72.7秒（Karma 1280×720）

### 手順1 分割の少ない球を置く（sphere）

sphere の Primitive Type を Polygon Mesh にし、Rows 5・Columns 10 と少なくする。縦を 0.36 に縮めると、上下がとがった宝石の形になる。

### 手順2 面を平らに見せる（facet）

facet で Unique Points と Post-Compute Normals を入れる。面ごとに点を分けて向きを付け直すので、なめらかな球ではなく、平らなカット面として光を返す。

### 手順3 置く場所を決め、1つずつ変える（attribwrangle）

grid の上に scatter で7点ばらまき（Relax を入れると重なりにくい）、attribwrangle で点ごとに大きさ（pscale）・向き（orient）・色（Cd）を決める。色は5色の表から順に選ぶ。最後の行で、宝石が床に埋まらないよう少し持ち上げる。

### 手順4 宝石を点に並べる（copytopoints）

copytopoints の左に宝石、右に点をつなぐ。点の pscale・orient で、大きさと向きの違う7つになる。色は、Target Attributes に1行足して「Apply to: Primitives」「Attributes: Cd」と書かないと移らない（既定では何も移さない）。

### 手順5 光を通す材質を当てる（material）

principledshader で Transparency 1（光を通す）、IOR 2.2（曲がり方。ダイヤは約2.4、ガラスは1.5）、Roughness 0 にする。Transmission Color の Use Point Color を入れると、面に移した色（Cd）が宝石の色になる。Dispersion 0.4 で、光が虹色に分かれる。材質は1つで7色すべてに使える。

### 落とし穴

- **facet を省くと、カット面にならない**: 球のままだと点は 32 個で、となりの面と点を共有しているので、Karma は面の境目をなめらかにつないで描く。facet で Unique Points を入れると点は 140 個に増え、面ごとに向きが切れる。これが宝石のきらめきの元。
- **copytopoints は、既定では色を移さない**: Target Attributes を空のまま複製すると、できた宝石に残る属性は P と N だけで、Cd が無かった。そのまま撮ると、7つとも無色のガラスになる。移したい属性は自分で書き足す。
- **透ける材質は撮るのが重い**: この絵は Karma 1280×720・128 サンプルで 73 秒。サンプルを下げると、宝石の中がざらつく。まず小さい解像度で色と形を決めてから、最後に大きく撮る。

## 実践40 焚き火を燃やす

薪と石を並べ、その真ん中から炎を出す。Pyro は既定のままだと炎が柱になって伸び続けるので、炎の寿命・浮き上がる力・冷め方の3つを下げて、焚き火の大きさにする（実験201）。

- 足すノード: 15個（材質3つ）
- 60 フレームの計算: 2.6秒
- 仕上がりを撮る時間: 20.7秒（Karma 1280×720）

### 手順1 薪を組む（copyxform）

tube で半径 0.07・長さ 0.9 の丸太を作り（Orientation を X 軸）、copyxform で 60度ずつ回し、0.06 ずつ持ち上げて3本にする。真上から見ると、真ん中で交わる星の形になり、上の薪が下の薪に乗る。

### 手順2 石で囲む（copytopoints）

circle（半径 0.55・12分割）の点に、mountain で少しでこぼこにした小さな球を copytopoints で並べる。炎の大きさの目安にもなる。

### 手順3 炎の出どころを作る（pyrosource）

薪の交わるところに、平たい球（半径 0.22・厚み 0.08）を置き、pyrosource の Initialize を Source Burn にする。球の中に点が詰まり、燃やすための値（burn・temperature）が付く。

### 手順4 点を升目にする（volumerasterizeattributes）

volumerasterizeattributes で点の値を升目（ボリューム）に移す。Attributes に burn temperature、Voxel Size は 0.03。Pyro は升目の上で計算する。

### 手順5 焚き火の大きさにして燃やす（pyrosolver）

pyrosolver で燃やす。既定のままだと炎が 1 秒に約 6 m 伸び続けるので、実験201 で決めた値に変える。Flame Lifespan 0.25・Buoyancy Scale 0.25・Cooling Rate 1。炎を揺らすのは Turbulence 3で、Use Control Field を切る（切らないと何も変わらない）。Create Flame Field と Flame Density（1）を入れて、炎から煙も出す。

### 手順6 炎の材質を当てて撮る（merge）

/mat に kma_pyroshader（Karma の炎用の材質）を作り、Enable Fire を入れて Intensity Scale を 1.5 にする（上げすぎると根元が白く飛ぶ）。Intensity Volume と Color Volume を flame に変え、Fire Color Ramp を黒→赤→橙→黄白にする。薪と石には principledshader。merge でまとめ、フレーム 60（2.5 秒）で撮る。炎の光で薪と石が照らされる。

### 落とし穴

- **既定の Pyro では焚き火にならない**: pyrosolver を既定のまま（Flame Lifespan 2 秒など）にすると、炎は 1 秒に約 6 m 伸び、3 秒たっても 14 m 近い柱のまま（実験201）。焚き火のような小さな炎は、寿命・浮き上がる力・冷め方の3つを下げて作る。
- **Turbulence は Use Control Field を切らないと効かない**: 既定では Turbulence は煙（density）の濃い所にだけ効く。炎の近くは煙が薄いので、強さを 1 にしても形は小数3桁まで同じだった（実験201）。
- **炎の材質は、既定では温度で光る**: kma_pyroshader の明るさ（Intensity Volume）と色（Color Volume）は、既定で temperature を見る。Cooling Rate 1 だと温度は発生源のすぐ上で下がるので、既定のまま撮ると、根元の平たい円盤だけが光って炎が写らなかった。flame に変える。
- **炎は升目の細かさで重さが決まる**: Voxel Size 0.03 で 60 フレーム回すのに 2.6 秒、炎の升目は 80 × 96 × 112。升を半分にすると升の数は 8 倍になる。形を決めるまでは粗く回す。

## 実践41 夜の街を並べる

格子の点にビルの箱を1つずつ置き、高さを中心ほど高く、少しずつばらつかせる。壁を窓の升目に割って、ところどころを光らせれば夜景になる。街全体を手で作らず、ルールで作る（プロシージャル）入り口。

- 足すノード: 11個（材質3つ）
- 建物: 149棟
- 面の数: 175,730
- 仕上がりを撮る時間: 33.7秒（Karma 1280×720）

### 手順1 区画の点を用意する（grid）

grid を 12 × 12、Rows・Columns を 13 にすると、1 おきに 169 個の点が並ぶ。1つの点に1棟を建てる。

### 手順2 高さと幅を決める（attribwrangle）

attribwrangle で、点ごとに建物の大きさ（scale、幅・高さ・奥行き）を決める。中心からの距離 d が小さいほど高く（5.0 → 0.4）、rand で 0.4〜1.3 倍にばらつかせる。12% の点は removepoint で消して空き地にする。p@orient = {0,0,0,1} で向きを固定する（理由は落とし穴に）。

### 手順3 1棟ぶんの箱を作る（box）

box を大きさ 1 のまま、Center の Y を 0.5 にする。底が地面（y=0）に乗るので、高さを伸ばしても地面に埋まらない。

### 手順4 点に箱を並べる（copytopoints）

copytopoints で、左に箱、右に点。点の scale で箱が伸び縮みして、高さの違うビルが建つ。

### 手順5 壁を窓の升目に割る（divide）

divide の Bricker Polygons を入れ、Size を 0.05 × 0.07 × 0.05 にする。壁も屋上も、窓くらいの大きさの升目に切れる。

### 手順6 窓を点ける（attribwrangle）

attribwrangle の Run Over を Primitives にし、壁向き（法線の Y が小さい）の升目のうち 16% を lit = 1 にする。点いた窓には暖かい色（7割）か白っぽい青（3割）を、明るさもばらつかせて入れる。

### 手順7 壁・窓・道の材質を当てる（merge）

principledshader を3つ。壁は暗い青みの灰色で少し映り込み、窓は Emission Intensity 3・Use Point Color（前の段の色で光る）、道はほぼ黒で映り込みを強く（濡れた路面）。material の Group に @lit=0 と @lit=1 を書き分けて当てる。

### 落とし穴

- **Center の Y を 0.5 にしないと、ビルが地面に埋まる**: box は中心が原点にあるので、そのまま高さを伸ばすと、上と下に同じだけ伸びて半分が地面の下に入る。底を y=0 に置くには Center の Y を 0.5（大きさの半分）にしてから並べる。
- **grid の点に並べると、ビルが横倒しになる**: grid の点には上向きの法線 N が付いていて、copytopoints は箱の Z（奥行き）を N にそろえる。向きを決めずに並べると、高さが横に倒れ、街全体の高さが 0.60 しかなかった（orient を固定すると 5.57）。高さを持つ物を並べるときは orient を入れておく。
- **窓の升目を細かくすると、面の数が一気に増える**: 149 棟を 0.05 × 0.07 の升目に割ると 175,730 面（うち点いた窓 22,630）。升目を半分（0.025 × 0.035）にすると 656,522 面で、割り直すだけで 12.3 秒かかった。遠景の街なら粗い升目で足りる。

## 実践42 カーテンを風になびかせる

布（Vellum の cloth）を1枚、上の端だけ留めて吊るし、窓の外から風を当てる。ひだを最初に付けておくと、風を受けたときにカーテンらしくふくらむ。ノードは布の3つ（形・性質・計算）が中心。

- 足すノード: 5個（布の部分）
- 48 フレームの計算: 11.1秒
- 仕上がりを撮る時間: 49.7秒（Karma 1280×720）

### 手順1 布の板を立てる（copyxform）

grid の Orientation を XY Plane（縦に立てる）、大きさ 0.85 × 2.2、Rows 56・Columns 24 にする。升目が細かいほど布はなめらかに曲がるが、計算は重くなる。copyxform で右へ 0.86 ずらした2枚目を作り、左右1組のカーテンにする。

### 手順2 ひだを付け、留める所を決める（attribwrangle）

attribwrangle で、横方向に sin の波を付けてひだにする。もう1行で、いちばん上の列の点を top というグループにまとめる。あとでここを留める。

### 手順3 布の性質を付けて、上を留める（vellumconstraints）

vellumconstraints の Constraint Type を Cloth にし、Pin Points に top と書く。これで上の列は動かず、ほかの点は布として引っぱり合う。出口は2つあり、左が布、右が「つながり（拘束）」。

### 手順4 風を当てて計算する（vellumsolver）

vellumsolver の左に布、真ん中に vellumconstraints の右の出口をつなぐ。Built-in Wind を入れて向きを (0.15, 0, 1)（窓から部屋の中へ）、Built-in Wind Speed 1.8、Built-in Wind Drag 0.3。Substeps は 5 にする（布が伸びすぎない）。再生すると布がふくらむ。フレーム 48（2 秒）で止めて撮る。

### 手順5 窓辺を組んで、材質を当てる（merge）

後ろに壁（grid）と、窓の形の光る板（Emission Intensity 1.4）、窓の桟（細い box 2本）を置き、上にカーテンレール（細い tube）を渡す。カーテンの材質は Transparency 0.45・IOR 1（光を通すが曲げない＝薄い布）、Sheen 0.5。窓の光を強くしすぎると、布を通した光まで白く飛んで布が消えるので、1.4 程度に抑える。

### 落とし穴

- **上を留めないと、布はそのまま落ちる**: Pin Points を空にすると、48 フレームで布のいちばん高い所が 2.25 m から 0.27 m まで下がった。Vellum の布は、留めた点がなければ全部が重力で落ちる。吊るす物は、まず留める所をグループにする。
- **風は Built-in Wind を入れないと吹かない**: Built-in Wind を切ると、布のいちばん手前は z = 0.03 m（ひだの厚みだけ）。入れると 1.02 m までふくらんだ。Built-in Wind Speed だけ上げても、Built-in Wind のチェックが切れていれば何も起きない。
- **Substeps 1 だと布が伸びる**: 風を切って吊るすだけにすると、長さ 2.2 m の布が Substeps 5 では 2.205 m、Substeps 1 では 2.240 m になった。1回の計算で動く量が大きいと、つながりを保ちきれず、布が自分の重さで伸びる。布は Substeps を上げて固さを保つ。
- **布の計算時間**: 点 2,688 個の布を Substeps 5 で 48 フレーム回すのに 11.1 秒。升目を倍にすると点は4倍になる。動きを決めるまでは粗い布で回す。

## 実践43 風船をふくらませる

しぼんだ風船を布（Vellum の cloth）で作り、内側から圧力（pressure）をかけてふくらませる。どこまでふくらむかは、圧力と、ゴムの伸びにくさの綱引きで決まる。色違いを束ねて、パーティーの風船にする。

- 足すノード: 13個（材質3つ）
- 24 フレームの計算: 22.7秒
- ふくらみ: 3.0倍
- 仕上がりを撮る時間: 219.4秒（Karma 1280×720）

### 手順1 しぼんだ風船の形を作る（attribwrangle）

sphere を Polygon Mesh・Rows 24・Columns 32 で置き、attribwrangle で下半分を細くしてしずく形にする。大きさはふくらんだ後の6割ほど（しぼんだ状態）。いちばん下の点は knot（結び目）というグループにする。

### 手順2 ゴムの膜にする（vellumconstraints）

vellumconstraints を Cloth にして、表面を伸び縮みする膜にする。Stretch の Stiffness を 1 × 10³（既定は 1 × 10¹⁰ でほとんど伸びない布）に下げて、ゴムのように伸びるようにする。Pin Points に knot と書いて、結び目を留める。

### 手順3 中に空気を入れる（vellumconstraints）

もう1つ vellumconstraints をつなぎ（左右の出口を両方）、Type を Pressure にする。閉じた袋の体積を保とうとする拘束で、Rest Length Scale を 3 にすると「今の3倍の体積が本来の大きさ」と思って、ふくらもうとする。

### 手順4 ふくらませる（vellumsolver）

vellumsolver に左右の出口をつなぎ、Gravity を 0（ヘリウム風船なので下に落とさない）、Substeps 5。再生すると、数フレームでふくらむ。体積は 5.1 L から 15.3 L（3.0 倍）になった。

### 手順5 色違いを5つ束ねる（copytopoints）

circle の5点に、attribwrangle で高さ・大きさ・傾き・色を付け、copytopoints でふくらんだ風船を並べる。色は Target Attributes で Points に Cd を移す（宝石の実践と同じく、既定では色は移らない）。

### 手順6 糸と重りを足して、材質を当てる（merge）

attribwrangle で、各風船の結び目から下の重りまで addprim で線を1本ずつ引く。並べるのに使った円の面は要らないので removeprim で消す。線の点に width（太さ 0.006）を付けると、Karma は線を糸として描く。風船の材質は Use Point Color で色を点から取り、Coat 1（表面のつや）でゴムらしい光り方にする。

### 落とし穴

- **Rest Length Scale が 1 のままだと、ふくらまない**: Pressure の Rest Length Scale を 1 にすると、24 フレーム後の体積は 5.1 L で、はじめ（5.1 L）のまま。圧力は「今の体積を保つ」力なので、ふくらませたいときは 1 より大きくする。
- **既定の布は、3倍にしても3倍にならない**: Rest Length Scale 3 でも、膜の Stiffness が既定（× 10¹⁰）だと体積は 2.13 倍にとどまった。× 10³ に下げると 3.00 倍。ふくらむ大きさは、圧力と膜の伸びにくさの綱引きで決まる。
- **結び目を留めないと、束ねる位置がずれる**: 結び目を留めると、ふくらんだあとも結び目は y = -0.130 m のまま。留めないと -0.076 m に動いた（細いしずくの下側が丸くふくらむので、結び目が 5 cm 上へ引き込まれる）。糸をつなぐ点は先に留めておくと、あとで糸を引く位置が合う。

## 実践44 ゼリーをぷるんと揺らす

ゼリーは表面だけでなく中まで詰まっているので、形を小さな四面体で埋めてから Vellum で揺らす。少し上から皿に落とすと、つぶれて戻る「ぷるん」が出る。撮るときは、四面体ではなく元のきれいな表面を動きに合わせて曲げる。

- 足すノード: 12個（材質2つ）
- 四面体: 6,991個
- 36 フレームの計算: 56.4秒
- 仕上がりを撮る時間: 443.6秒（Karma 1280×720）

### 手順1 ゼリーの形を作る（remesh）

tube で下が広く上が狭い円柱（半径 0.3 → 0.22、高さ 0.28）を作り、皿の 0.2 m 上に置く。remesh の Target Size を 0.03 にして、表面をそろった三角形にする。細長い面が残っていると、次の四面体づくりがゆがむ。

### 手順2 中を四面体で埋める（tetrahedralize）

tetrahedralize を既定のまま（Mode は Conform to Surface）つなぐ。表面の三角形をそのまま外側に使って、中を小さな四面体（三角すい）で埋める。ゼリーの「中身」がここでできる。

### 手順3 柔らかさと、体積を保つ力を付ける（vellumconstraints）

vellumconstraints を2つ重ねる。1つ目は Tet Stretch（四面体の辺が伸び縮みする）で、Stiffness を 1 × 10⁴ と柔らかくする。2つ目は Tet Volume（四面体ごとの体積を保つ）で既定のまま。つぶれても体積が減らないので、横にふくらんで戻る。

### 手順4 皿に落として揺らす（vellumsolver）

vellumsolver に左右の出口をつなぎ、Ground Plane を入れて y = 0 に床を作る。Substeps 5。再生すると、落ちて床に当たり、ぷるんとつぶれて戻る。高さ 0.280 m のゼリーが、フレーム 8 でいちばんつぶれて 0.196 m になった。

### 手順5 きれいな表面を、動きに合わせて曲げる（subdivide）

四面体は中身の計算用で、そのまま撮ると面がでこぼこに見える。pointdeform の左に元の表面（remesh の出力）、真ん中に 動く前の四面体（tetrahedralize の出力）、右に計算中の形をつなぐ。表面が、四面体の動きにそって曲がる。最後に subdivide（1回）で面を細かく割って、角ばりを消す。

### 手順6 ゼリーと皿の材質を当てる（merge）

ゼリーは principledshader で Transparency 1・IOR 1.35（水に近い）、Roughness 0.03。Transmission Color を赤、Transmission Distance を 0.12 にすると、厚い所ほど濃い赤になる。皿は白く、Coat 1 でつやを出す。

### 落とし穴

- **硬すぎると、ぷるんとしない**: Tet Stretch の Stiffness を既定の × 10¹⁰ にすると、いちばんつぶれても高さ 0.280 m（はじめ 0.280 m）で、ほとんど形が変わらない。× 10⁴ では 0.196 m までつぶれた。ゼリーの柔らかさはここで決まる。
- **Tet Volume がないと、深くつぶれて戻りきらない**: 2つ目の Tet Volume を外すと、いちばんつぶれた高さは 0.146 m、36 フレーム後も 0.244 m。付けたときは 36 フレーム後に 0.263 m まで戻った。体積を保つ力がないと、深くつぶれ、戻りも足りない。
- **四面体の数が重さを決める**: remesh 0.03 の表面から、四面体は 6,991 個できた。36 フレームの計算は 56.4 秒。Target Size を半分の 0.015 にすると 30,420 個（4.4 倍）。揺れを決めるまでは粗くする。

## 実践45 夕暮れの海の波を作る

海はシミュレーションしなくても作れる。風の強さから波の混ざり方（スペクトル）を決め、平らな板の点をその通りに動かすだけ。波のとがった所に白い泡の色を付け、低い夕日を逆光にすると、水面がきらめく。

- 足すノード: 10個（材質3つ）
- 波の高低差: 3.52 m
- 仕上がりを撮る時間: 75.8秒（Karma 1280×720）

### 手順1 平らな板を敷く（grid）

grid を 60 × 60 m、Rows・Columns 500（升目 12 cm）にする。波は点を動かして作るので、升目が粗いと細かい波が出ない。

### 手順2 風から波の設計図を作る（oceanspectrum）

oceanspectrum は、風の強さと向きから「どの大きさの波がどれだけ混ざるか」を作る。Wind の Speed を 9（m/秒、やや強い風）、Chop を 0.9（波の頭をとがらせる）にする。Grid Size 50 は、この設計図が何 m ごとにくり返すか。

### 手順3 設計図どおりに点を動かす（oceanevaluate）

oceanevaluate の左に板、右に oceanspectrum をつなぐ。Time に $T（今の秒数）を書くと、再生に合わせて波が進む。Cusp Attribute を入れると、波の頭がとがって折れそうな所に cusp という値が付く。泡の目印に使う。

### 手順4 波の頭を白くする（attribwrangle）

attribwrangle で、cusp が小さい所は深い青緑、大きい所ほど白に近づける。smooth(0.4, 0.7, …) は、0.4 より下は 0、0.7 より上は 1 に、間をなめらかにつなぐ（しきい値は落とし穴を参照）。

### 手順5 空を置く（attribwrangle）

海は空を映して色が決まるので、先に空を作る。半径 400 m の sphere で全体を包み、attribwrangle で高さに合わせて色を付ける。水平線の近くは橙、上ほど夜の青。奥の低い所に、小さな球を夕日として置く。

### 手順6 水の材質を当てる（merge）

principledshader で Use Point Color（前の段の色を使う）、Roughness 0.02・Reflectivity 1・IOR 1.33（水）。水面は空と夕日を映して色が決まるので、材質の色は暗くしておく。空の球には光る材質（Use Point Color で色を点から取る）、夕日の球には強い光（Emission Intensity 25）。

### 落とし穴

- **Time に $T を書かないと、波が止まる**: Time を 0 のままにすると、フレーム 1 と 24 で点の位置の差は最大 0.0000 m（まったく同じ）。oceanevaluate は「何秒目の波か」を Time で受け取るので、$T を書いて再生とつなぐ。
- **海は Grid Size ごとに同じ模様をくり返す**: 50 m 離れた2点で波の高さをくらべると、差は 0.000000 m（高さ -0.154 m）で同じだった。Grid Size 50 の設計図は 50 m ごとにくり返すので、50 m より広く写すと、同じ波の並びが2回出てくる。撮る範囲が Grid Size を超えるときは、Grid Size を大きくしておく。
- **泡のしきい値を低くすると、海が白っぽくなる**: 風 9 m/秒・Chop 0.9 で、いちばん高い所と低い所の差は 3.52 m、cusp が 0.15 を超えた点は全体の 46.3% もあった。はじめ smooth(0.15, …) にしたら、海の半分近くに泡の白が混ざった。0.4 を超える点は 6.3% で、泡らしい量になる。25 万点の板を動かすのに 0.19 秒。

## 実践46 石灯籠に雪を積もらせる

雪は上から降るので、積もるのは「上を向いていて、上に何もない面」だけ。その面に粒をまき、粒をまとめて1つの塊（VDB）にすると、角の丸い、ぽってりした雪になる。形を選ばず、どんなモデルにも使える。

- 足すノード: 18個（材質3つ）
- 雪の粒: 20,644個
- 雪の面: 80,230枚
- 仕上がりを撮る時間: 476.8秒（Karma 1280×720）

### 手順1 石灯籠を組む（merge）

box・tube・sphere を積んで灯籠にする。屋根は tube の Columns を 4、上の半径を小さく（0.03）すると四角すいになる。45 度回して箱と向きをそろえる。火袋（明かりの箱）だけは、あとで光る材質を当てるので別にしておく。

### 手順2 上を向いた面だけ残す（attribwrangle）

attribwrangle の Run Over を Primitives にして、面の向き（prim_normal）の上向きの成分 y が 0.5 より小さい面を消す。壁や下向きの面が消え、屋根や台の上だけが残る。

### 手順3 雪の粒をまく（scatter）

scatter で、残った面に 4 万個の点をまく。1つの点が1粒の雪になる。

### 手順4 屋根の下の粒を消す（attribwrangle）

attribwrangle の2つ目の入力に灯籠全体をつなぎ、各点から真上へ光線を飛ばす（intersect）。何かに当たれば、その点は屋根の下なので消す。残った点には粒の大きさ pscale（約 2.8 cm）を付ける。

### 手順5 粒をつないで雪の塊にする（convertvdb）

vdbfromparticles で粒を1つの形（VDB）にまとめる。Voxel Size は 0.006（粒の半径の 1/5 くらい）。vdbsmoothsdf で角を丸め（Iterations 6）、convertvdb の Convert To を Polygons にして面に戻す。

### 手順6 雪の地面を敷き、材質を当てる（merge）

grid を少し持ち上げ（起伏で床の下にもぐらないように）、mountain で起伏を付けて雪の地面にする。雪の材質は白く、Subsurface 0.6（光が少し中に入る）で青みを足す。火袋には Emission Intensity 2 の暖かい光（強くすると白く飛ぶ）。石は暗い灰色。

### 落とし穴

- **屋根の下にも雪が積もってしまう**: 上向きの面は、屋根に隠れた中台や火袋の上にもある。真上への光線で調べると、まいた 40,000 点のうち 19,356 点が屋根などの下にあった。消さないと、屋根の下に雪の塊ができる。
- **向きのしきい値で、雪の付く面が変わる**: N.y < 0.5 で消すと、残る面は 105 枚。0 にする（下向きだけ消す）と 189 枚が残り、壁のような縦の面にまで粒がまかれる。急な面に雪は残らないので、0.5 前後から始める。
- **Voxel Size で、雪の細かさと重さが決まる**: Voxel Size 0.006 で雪の面は 80,230 枚（0.8 秒）。倍の 0.012 にすると 17,680 枚（0.1 秒）。形を決めるまでは粗くして、最後に細かくする。

## 実践47 花火を打ち上げる

夜空で丸く開く「菊」の花火を作る。球の表面に並べた点を一斉に外へ飛ばし、重力と空気抵抗で垂れさせ、通った跡を線にすると尾ができる。1発できたら、時間と場所をずらして3発に増やす。

- 足すノード: 15個（dopnet の中に5個）
- 星の数: 320個 × 3発
- 60 フレームの計算: 0.3秒
- 仕上がりを撮る時間: 3.2秒（Karma 1280×720）

### 手順1 玉の中の「星」を並べる（scatter）

sphere（半径 1 m）の表面に、scatter で 320 個の点をまく。1つ1つが、花火の玉に詰まった「星」（燃えながら飛ぶ火薬の粒）になる。Relax Iterations を入れておくと、点どうしが離れて、開いたときに穴や固まりができにくい。

### 手順2 外向きの速さと色を付ける（attribwrangle）

attribwrangle で、点ごとに v（速さと向き）を付ける。向きは球の中心から外、速さは speed = 34（m/秒）を星ごとに 88〜100% の範囲でばらつかせる。全部同じ速さだと、コンパスで描いたような不自然な球になる。色 Cd は金色（1, 0.72, 0.32）。

### 手順3 重力と空気抵抗で飛ばす（dopimport）

dopnet の中に POP を組む。popsource は Emission Type を All Points、Impulse Activation に式 $FF == 1 を入れて、1 フレーム目だけ 320 個を一度に生む。Initial Velocity は Use Inherited Velocity（前の段で付けた v をそのまま使う）。寿命 Life Expectancy 2.2 秒・Life Variance 0.5 で、消える時間をばらけさせる。popforce で下向き 9.81 の重力、popdrag の Air Resistance 0.45 で空気抵抗を入れる。空気抵抗があると最初だけ速く広がり、すぐ減速して垂れる。花火らしさはここで出る。0.9 秒後の広がりは約 13 m。外の dopimport で結果を取り出す。

### 手順4 通った跡を線にして、尾を付ける（attribwrangle）

trail の Result Type を Connect as Polygons、Trail Length を 18 にすると、星ごとに「今までの 18 フレーム分の位置」をつないだ線ができる。これが火の粉の尾になる。次の attribwrangle で、線の先頭ほど白く太く、うしろほど赤く細くする（width 0.01 → 0.00 m）。さらに寿命の終わりに向けて全体を暗くすると、燃え尽きて消えていく。

### 手順5 時間と場所をずらして3発にする（merge）

timeshift の Frame に $F - 7 のような式を入れると、同じ花火を 7 フレーム遅れて再生できる。xform で場所をずらし、もう1本の attribwrangle で色を赤・水色に置き換える。計算（POP）は1回だけで、3発とも同じ結果を使い回すので軽い。最後に merge でまとめる。

### 手順6 光る材質を当てる（material）

principledshader の Emission Intensity を 0.9、Emission Color の Use Point Color を入れる。線の色（Cd）がそのまま光の色になる。Base Color は黒にして、光以外の見え方を消す。

### 落とし穴

- **空気抵抗を入れないと、花火に見えない**: Air Resistance を 0 にすると、フレーム 22 の広がりは約 13 m（0.45 のときは約 13 m）。減速しないので星がまっすぐ飛び続け、ただ大きくなる球になる。本物は最初に勢いよく開き、すぐ止まって垂れる。
- **寿命をばらけさせないと、一斉に消える**: Life Variance 0 では、フレーム 40 に 320 個あった星が、フレーム 60 には 69 個。0.5 では 40 で 320 個、60 で 69 個。ばらつきがあると、少しずつ消えていく。
- **尾の点数は、星の数 × Trail Length**: 320 個の星に Trail Length 18 で、尾の線の点はフレーム 22 で 5,760 個。尾を長くすると点が同じ割合で増える。3発にしても計算は1回で済むのは、timeshift で使い回しているから。

## 実践48 苔むした石を作る

石の上を向いた面にだけ、まだらに苔を生やす。「上を向いている度合い」と「まだらのノイズ」を掛け合わせて生える場所を決め、そこに短い毛を密に立てる。色だけで塗るより、毛を立てたほうが苔のふかふかした感じが出る。

- 足すノード: 12個（材質2つ）
- 毛の数: 90,000本
- 仕上がりを撮る時間: 39.3秒（Karma 1280×720）

### 手順1 石の形を作る（normal）

sphere（Polygon Mesh、半径 0.55 × 0.32 × 0.45、Rows 80・Columns 160）をつぶれた丸石にする。mountain を2つ重ね、1つ目（Height 0.16・Element Size 0.45）で大きなうねり、2つ目（Height 0.04・Element Size 0.07）で細かいでこぼこを付ける。最後の normal で面の向き（N）を計算し直す。次の段で「上を向いているか」を見るのに使う。

### 手順2 苔の生える場所を決める（attribwrangle）

attribwrangle で、点ごとに moss（0〜1）を作る。まず N.y（面が上を向いている度合い）が 0.2 以下なら 0、0.75 以上なら 1 にする。これにノイズで作ったまだらを掛けると、上の面は厚く、縁はまだらに薄くなる。色 Cd も、moss に合わせて灰色から濃い緑へ変える（毛の根元が見える所の色）。石の灰色には別のノイズで濃淡を付け、のっぺりした粘土に見えないようにする。

### 手順3 苔の毛の根元をまく（scatter）

scatter で 90,000 個の点をまく。Use Density Attribute を入れて Density Attribute を moss にすると、moss の大きい所ほど点が多く、0 の所には1つも出ない。点は、面の N などの属性を引き継ぐ。

### 手順4 短い毛を立てる（attribwrangle）

もう1つの attribwrangle で、点ごとに3つの点をつないだ短い線（毛）を作る。向きは面の向き N に、ランダムな傾きを少し足したもの。長さは length = 0.014（1.4 cm）を 50〜130% にばらつかせ、先を少しだけ下へ垂らす。根元は暗い緑、先は明るい黄緑にし、太さ width は根元 1.6 mm から先へ細くする。最後に元の点を消す。

### 手順5 材質を当てて合わせる（merge）

石と苔に別々の principledshader を当てる。どちらも Base Color を白にしておくと、点の色 Cd がそのまま色になる（Use Point Color が既定で入っている）。石は Roughness 0.85 でつやを消し、苔は Sheen 0.6 で、毛の表面がふわっと明るく光る感じを足す。merge で石と苔を1つにする。

### 落とし穴

- **形を変えたら、N を作り直す**: normal を外すと、mountain の出力には N が無い（測った）。wrangle の v@N は 0 になり、N.y で決める苔の場所が1つも出ない。形を変えたあとは、N を作り直してから向きを読む。
- **Force Total Count は「苔のある所にだけ」まかれる**: Density Attribute を使っても、点の総数は Force Total Count のまま（90,000 本）。苔の場所が狭いと、同じ数が狭い所に詰まって濃くなる。広く生やすなら数も増やす。
- **毛の数が重さを決める**: 90,000 本の毛は、点にすると 270,000 個。Karma で 1280×720 を撮るのにかかった時間は上の表のとおり。試すうちは STRANDS を減らして速く回し、最後に戻す。

## 実践49 窓ガラスを割る

板ガラスに球をぶつけて割る。rbdmaterialfracture を Glass にして当たる点を渡すと、そこから放射状と同心円のひびが入る。枠に触れている破片だけ動かないようにしておくと、真ん中が砕けて飛び、外側の破片が枠に残る。

- 足すノード: 18個（材質2つ）
- 破片: 119個
- 48 フレームの計算: 0.8秒
- 仕上がりを撮る時間: 68.8秒（Karma 1280×720）

### 手順1 ガラス板と、当たる点を置く（merge）

box で 1 × 1.4 m、厚さ 8 mm の板を立てる（窓1枚ぶん）。add で点を1つだけ作り、球が当たる所（0.12, 0.9, 0）に置く。ひびはこの点から広がる。

### 手順2 ガラスの割れ方で割る（rbdmaterialfracture）

rbdmaterialfracture の Material Type を Glass にし、4番目の入口（Impact Points）に当たる点をつなぐ。Use Input Points を入れると、その点を中心に 放射状のひび（既定 20 本）と、それをつなぐ同心円のひびが入る。破片は 119 個になった。右の出口には、破片どうしをくっつけておく「つながり」が出る。

### 手順3 球を用意し、枠に触れる破片を止める（attribwrangle）

sphere（半径 6 cm）を当たる点の 70 cm 手前に置き、attribwrangle で名前 ball と速さ v = (0, 0, −14)（ガラスへ向かって秒速 14 m）を付ける。merge でガラスとまとめ、pack の Pack By Name を入れて、同じ name の面を1つの塊（破片1つ）にまとめる。最後の attribwrangle で、塊の外枠が板の縁から 3 cm 以内に入るものを active = 0（動かない）にする。21 個が止まった。

### 手順4 ぶつけて割る（rbdbulletsolver）

rbdmaterialfracture の右の出口（つながり）に attribwrangle をつなぎ、Run Over を Primitives にして strength を 0.8 に下げる。既定のままだと強すぎて、球が跳ね返るだけで1枚も割れなかった。rbdbulletsolver の左に塊、真ん中に弱めたつながりをつなぎ、Ground Plane を入れる。球が当たると、そのまわりのつながりが切れて破片が飛び、遠くの破片はつながったまま枠に残る。48 フレームで、119 個のうち 41 個が動いた。

### 手順5 枠を付けて、ガラスの材質を当てる（merge）

細い box 4本で木の窓枠を作る。ガラスは principledshader で Transparency 1・IOR 1.52（板ガラス）、Roughness 0。Transmission Color を少し青緑に、Transmission Distance 0.3 にすると、破片の厚い縁がうっすら緑に見える（本物の板ガラスの色）。unpack で塊を元の面に戻してから材質を当て、もう1つの material で Group を @name=ball にして、球だけ鉄にする。

### 落とし穴

- **枠で止めないと、板ごと倒れる**: hold_edges を外すと、48 フレームで 119 個のうち 119 個が動いた。ガラス板はただ床に立っているだけなので、つながったまま倒れる。縁の破片を active = 0 にして、枠にはまっている状態を作る。
- **つなぐ力（strength）で、割れる広さが決まる**: strength 0.8 で 41 個が動いた。同じ場面で測ると、1.5 で 7 個、2.5 で 1 個、5 以上では 0 個（球が跳ね返るだけ）。小さいほど広く割れる。
- **放射状のひびの数で、破片の数が決まる**: Radial Crack Number 20（既定）で 119 個、8 にすると 37 個。放射状のひびの間を同心円のひびが切るので、本数を減らすと大きな三角の破片になる。

## 実践50 テーブルクロスを掛ける

平らな布（Vellum の cloth）を机の少し上に置いて落とす。机を「ぶつかる物」として渡すだけで、天板の上は平らに、縁からはまっすぐ垂れ、四隅には大きなひだができる。布を細かく割るほど、ひだは細かくなる。

- 足すノード: 13個（材質2つ）
- 布の点: 15,651個
- 72 フレームの計算: 72.6秒
- 仕上がりを撮る時間: 51.9秒（Karma 1280×720）

### 手順1 机を作る（merge）

box で天板（1.2 × 0.04 × 0.8 m、高さ 0.74 m）と、細い脚を4本作り、merge でまとめる。この机は、あとで布が「ぶつかる物」になる。

### 手順2 布を机の上に置く（grid）

grid（1.9 × 1.45 m）を天板より 12 cm 上に置く。天板より縁ごとに 33〜35 cm 大きいので、そのぶんが垂れる。Rows 110・Columns 140 と細かく割る。布は網の線でしか曲がれないので、粗いとひだが角ばる。Rotate Y を 4 度だけ回して、机とぴったり揃えない（揃いすぎると作り物に見える）。

### 手順3 机にぶつけて落とす（vellumsolver）

vellumconstraints の Constraint Type を Cloth にする（布として引っぱり合うつながりが付く）。vellumsolver には3本つなぐ。左に布、真ん中に vellumconstraints の右の出口（つながり）、右に机。右の入口は「ぶつかる物」で、布は机を通り抜けずに乗る。Ground Plane も入れ、Substeps 5。72 フレーム（3 秒）で落ち着き、布の角は天板から 0.49 m 下まで垂れた。

### 手順4 なめらかにして、厚みを付ける（polyextrude）

subdivide（1回）で網をさらに細かく割り、ひだの折れ目の角を消す。polyextrude で Distance 0.002（2 mm）押し出し、Output Back を入れて裏面も残す。厚みのない布は、縁が紙のように薄く見える。

### 手順5 材質を当てる（merge）

布は principledshader で生成りの白（0.86, 0.84, 0.79）、Roughness 0.8、Sheen 0.5（布の毛羽が光をふわっと返す）。机は濃い茶色で Roughness 0.45。

### 落とし穴

- **机を右の入口につながないと、布は床まで落ちる**: vellumsolver の右の入口を空にすると、72 フレームで布のいちばん高い所は 0.01 m（床の上に重なった）。机は見えているだけでは布に当たらない。ぶつかる物は、必ず右の入口に渡す。
- **細かさと重さ**: Rows 110・Columns 140（点 15,651 個）で 72 フレームの計算は 72.6 秒。Rows 44・Columns 56（点 2,565 個）では 26.9 秒。粗いうちに落ち方を決めて、最後に細かくする。
